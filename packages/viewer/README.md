# @wastech-mdlint/viewer

A local web viewer for a repository's Markdown. It serves exactly the corpus [wastech-mdlint](https://github.com/VladimirMakarevich/wastech-mdlint#readme) lints, as pages with the document tree, highlighted code, Mermaid diagrams, ECharts charts, an outline, backlinks, a graph of the links between documents, full-text search, the linter's findings with prompts to fix them, a dashboard of the whole corpus and a review of what the current branch changed in it, lets the linter's config be edited with a preview of what it would report, lets the reader set the fonts, sizes and margins of the text, and reloads an open page when its file changes.

**Experimental.** The package is `private` in this repository and is not published yet.

## Run it

From this repository, after `npm run build`:

```bash
node packages/viewer/dist/index.js path/to/repository
```

It prints the address, by default `http://127.0.0.1:4180/`. The root opens the repository's `README.md`.

| Option | Meaning |
| --- | --- |
| `[path]` | Repository directory; the current directory when omitted. |
| `-p, --port <n>` | Port. Without it the viewer takes `4180`, or the next free port above it. `0` picks any free port. |
| `--host <host>` | Address to bind. The default `127.0.0.1` keeps the documents on this machine; any other address lets the network read them, and the viewer says so when it starts. |
| `-c, --config <file>` | The `wastech-mdlint.config.json` to use instead of the one found in the repository. |
| `--no-watch` | Do not watch files or reload pages. |
| `--allow-config-writes` | Let the config page save changes to the config file. Off by default, and refused together with a `--host` that is not a loopback address. |
| `--base <ref>` | The branch, tag or commit the Changes section compares with. Without it: the branch `origin/HEAD` names, then `main`, then `master`. A name that matches nothing is reported when the viewer starts, which then serves everything else as usual. |
| `--state-dir <dir>` | Where review marks are kept. Without it: `%LOCALAPPDATA%\wastech-mdlint\viewer` on Windows, `~/Library/Application Support/wastech-mdlint/viewer` on macOS, `$XDG_STATE_HOME/wastech-mdlint/viewer` (or `~/.local/state/wastech-mdlint/viewer`) elsewhere. Inside, one folder per clone, named after it and shared by all its worktrees; deleting that folder clears its marks. |

## What it shows

- **The linted corpus.** The config's `include`, `exclude` and `respectGitignore` decide which files are documents, the same way `wastech-mdlint lint` decides, including dot-directories such as `.claude/` when the config includes them. Without a config, every Markdown file outside the default excludes.
- **Links that agree with the linter.** A relative or root-relative link resolves the way REF-001 resolves it, and heading ids are the slugs REF-002 checks anchors against, so a link the linter accepts works on the page. Links and images written as raw HTML (`<a href>`, `<img src>`) resolve the same way. A link to a folder opens that folder's `README.md`. A link whose target does not exist, or is not served (see below), is underlined in red.
- **Linked source files.** A link from a document to a non-Markdown file opens it as highlighted source with line numbers; `#L42` and GitHub's `#L12-L20` ranges land on and mark those lines. Images a document embeds are served as they are. A file that an `exclude` pattern or a `.gitignore` covers is not served — every `.gitignore` counts here, whatever `respectGitignore` says, since it is where a repository names what it keeps to itself — and neither is a Markdown file outside the corpus.
- **Code and diagrams.** Fenced code is highlighted on the server with Shiki in light and dark themes, and every highlighted block — in a document, a linked source file or the config page — has a **Copy** button in its corner, shown on hover, that copies its code without the line numbers. A `mermaid` block is drawn in the browser; if it cannot be drawn, its source stays on the page with the reason.
- **Charts.** An `echarts` block holds an [ECharts option](https://echarts.apache.org/en/option.html) written as JSON — strict JSON, so no functions, comments or unquoted keys — and is drawn in the browser in the page's theme. A block that is not a JSON object says why above its source, with or without script. Tooltips are drawn as text on the chart, so markup in a `formatter` shows as written rather than as HTML, while `<br/>` still breaks the line.
- **Link graph.** `Graph` in the header opens every document as a node and every linked pair as a line, from the same context graph `wastech-mdlint graph` reports; hovering a document lights its links and names its neighbors without dimming the rest. Documents are laid out several node widths apart, the much-linked ones with room in proportion to their size so that none lands on another, and a large graph opens zoomed out to fit; only the most linked-to documents are named until the wheel zooms in far enough, and then the other names grow in. The folder picker narrows it to one folder and colors that folder's subfolders apart; dragging pans, a click opens the document. Opened from a document, the graph centers on it, draws its own links as arrows in the accent color, and turns every document outside its direct neighbors gray. A save that changes a link redraws it. In a git work tree, **Show the branch's changes** (`?changes=1`) rings each changed document in its letter's color and every unchanged one the change reaches in a dashed ring, draws the pairs the branch linked in green and the ones it unlinked as dashed red lines that pull nothing together, and the small graph beside a changed document does the same while its page shows its changes. Without script, the page lists the documents in view, changed ones with their letter, and the same data is at `/api/graph?folder=…&focus=…&changes=1`.
- **Copying a path.** The button beside the path in the header, and beside the config file on the config page, copies the path relative to the repository, as links and findings name it, or the absolute path on this machine. The absolute path is offered only when the viewer is bound to a loopback address.
- **Source lines.** Beside every block and list item, in the right margin, the line it starts on in the Markdown file, counted from the top with front matter included — the line an editor and a finding name. Selecting and copying the article leaves the numbers out, and they are hidden on a narrow screen and in print.
- **Front matter** as a card above the article, an **outline** of the document's `h2` and `h3` headings that marks the section being read as the page scrolls, and **backlinks**: the documents that link to this one, from the context graph.
- **Local graph.** Above the outline, a small graph of the document, the documents it links to and the ones linking to it, with the links among them (`/api/neighbors?path=…`). The neighbors sit evenly on a ring around the document, its own links drawn as fine arrows and the ones among them fainter still; a document with many neighbors opens zoomed out. Dragging pans it and Ctrl or ⌘ with the wheel, or a trackpad pinch, zooms it, while the plain wheel keeps scrolling the page. A click on a neighbor opens it, and a link below opens the full graph centered on the document. It is drawn only where the side column shows, so a narrow screen never loads it.
- **Search.** The box in the header searches titles, headings, paths and text, Cyrillic included, and matches a word while it is still being typed. `Ctrl+K` (or `/`) focuses it, the arrow keys pick a result and `Enter` opens it at the heading nearest the match. Without script, the same box opens a results page.
- **Lint findings.** The config's rules run over the corpus in the background. A document with findings shows them in a panel above its text — severity, rule, message and the heading to jump to — and the tree shows a count beside every file that has any. Both refresh on their own after each save.
- **Fix prompts.** Each finding in the panel has a **Prompt** menu, and so do the panel for all of the document's findings and every dashboard row with findings. It copies a prompt to hand to a coding agent. A size finding (SIZE-001, or LLM-001's context budget) offers three: compress the text without losing a fact, split the file by meaning, or raise the budget for that one path — the last spells out the config edit, including that SIZE-001 uses the first matching override and that a metric it leaves out falls back to the top-level budget. Any other finding offers a prompt to fix it in the document rather than silence it. The prompts follow the same policy as the agent rule `wastech-mdlint init` writes, name the config and the command that runs the linter in this repository, and are written from the latest lint run when the menu opens.
- **Dashboard.** `Dashboard` in the header lists every document with its errors, warnings and the rules behind them, its size in KB, lines and tokens (the counts SIZE-001 checks), how many documents link to it and how many it links to, and whether it is an orphan (nothing links to it), a dead end (it links nowhere), on a link cycle (as GRP-001 sees them) or outside the main group of linked documents. The filters pick documents with errors and/or warnings, from chosen rules (a severity and a rule are judged on the same finding), within a size, line or token range (both bounds included, a KB being 1024 bytes), with chosen link flags, in a folder, or with a text in the path; a column header sorts by that column. It works as a plain form without script; with script every change applies as it is made, and findings and sizes follow each save. The address carries the filters, `/api/dashboard?…` answers the same query as JSON, and the download links give the selection as CSV or JSON. In a git work tree a Branch column shows each document's letter when the branch changed it and the findings the change gave it and took from it, an unchanged document included, and **Changed in this branch** (`changed=1`) keeps only the changed ones; both are in the CSV and JSON. A switch above the tree shows only the files with findings.
- **Changes.** In a git work tree, `Changes` in the header reviews what the current branch changed in the corpus, against where it left the base branch (the merge-base, as GitHub compares a pull request), so commits that landed on the base afterwards never show as changes here. Only the linted documents are listed, however many other files the branch touched: the config file first when it changed, then the documents loaded into every agent session (LLM-001's entrypoints and everything they import, marked _every session_), then the rest by how many documents reach them through links, most first. Each has its diff, with the changed words of a paragraph marked inside the line, and in a table row the changed cell, whatever padding a formatter realigned around it; a long diff starts folded. Markdown files the config leaves out are counted above the list, so a narrowed scope never reads as no changes. Below the comparison it says what the change does to the context: the findings it adds and removes — the base linted as the merge-base held every document, a finding moved by an edit above it, or surviving an edit to its own line, counted as the same finding — and, for every LLM-001 entrypoint whose session context moved, its total against the budget (`CLAUDE.md eager context 8921 → 10.7k tokens (+1856, budget 10k)`; a count from ten thousand up in thousands, cut down rather than rounded, so a total just under its budget never reads as the budget), in the warning color when over it. Each row of the list shows its findings, a document given new errors moves up after the ones every session loads, and each card shows its document's tokens, lines and KB before and after, the findings it gained and lost, and the links it made and broke. **Affected documents** lists the documents the branch did not change that it still reaches: those with new findings — a heading renamed elsewhere broke their anchor, an entrypoint's imports grew — those whose `file.ts#L12-L20` link now points at code lines the branch edited or moved, and, folded, those that link to a changed document. When the config changed, its card adds what the config change alone does to the current documents' findings, through the same comparison the config page's preview uses. With **Commits only** the context is compared up to the last commit too, the uncommitted edits left out. **Work tree** includes uncommitted and untracked files; **Commits only** compares up to the last commit (`?worktree=0`). The header shows how many documents changed, the tree marks each with a letter — A, M, R — and a switch shows only those, and a changed document's page shows its changes in place (below). `/api/changes` lists the same as JSON, every finding in full, and `/api/changes/diff?path=…` gives one document's diff. Outside a git work tree, or without `git` on the path, there is no Changes section; when it cannot compare — no base branch, a shallow clone, a repository git refuses to read — the page says why and how to fix it.
- **Changes on a document's page.** Above a changed document's text, a line says what the branch did to it — its letter, the lines added and removed, a link to its card on the Changes page — and switches between three views, kept in the address so a reload or a shared link shows the same one. **Rendered** marks each changed block with a bar at its left edge, amber where it was edited and green where it is new: the innermost block only, so an edited list item is marked and not its list, while a table, a code block and the front matter card are each marked whole. Each block the branch removed is put back where it stood, folded (`2 blocks removed`), its links resolved against the current documents, so a link that only worked before the change shows as missing; with script, a click on a bar opens that block's hunks from the source diff below it. The outline marks every section that holds a change. **Source** (`?diff=source`) shows the document's diff in place of its text, and **Off** (`?diff=off`) the page without marks. A document the branch added gets the line but no marks, since every block would carry one. All of it is rendered on the server, so it reads the same without script; in print the bars stay as a left border and the removed blocks are left out.
- **Review marks.** In a git work tree, every card on the Changes page and the line above a changed document have a **Viewed** box; `v` checks or clears it — on the Changes page for the card being read. A mark records the text the page showed, not a time or a commit: the document stays reviewed while its text is that text — on another branch, after a rebase, a restart or a rename without edits — and turns **Changed since review** the moment it differs. A reviewed card folds to its header. The header's Changes count becomes what is left (`3/12`), the tree puts a dot beside every changed file not yet reviewed (amber once it changed since its review) and **Only files left to review** shows only those, and `n` and `p` open the next and previous one in the Changes page's order. **Compare with: My last review** (`?since=review`) shows, on the Changes page and in each view of a document's page, what changed since the version last reviewed; a document never reviewed, or whose reviewed text is no longer kept, is compared with the base branch, and the card says so. **Reset review** forgets the marks of every document listed, earlier versions included. `/api/changes` gives each document's status and the hash a mark names, and `/api/changes/diff?path=…&since=review` the diff since the review. There are no marks outside a git work tree, or with a `--host` that is not a loopback address.
- **Config.** `Config` in the header shows the config file and every rule in the registry with its description. **Show in folder** opens the system's file manager with the file selected (on Linux, the folder that holds it), and **Open in default app** opens it in the application the system uses for it; both only when the viewer is bound to a loopback address. With script, a form built from the config schema edits the files, the rules — adding one from the registry, removing one, its severity and options — custom rules, settings and compile options; a Text view edits the file as a whole. A setting with two or three choices, such as a rule's severity or `respectGitignore`, is a row of segments, one click to change; a longer list is a menu. Each change is checked by the linter's own config loader, and the preview says what the change would report: the findings it adds and removes, per rule and one by one, or the loader's reason when the config would not load. The changed file can be copied or downloaded, or saved when the viewer was started with `--allow-config-writes`. Only the edited values change in the file: every comment and the layout of the rest stay as written. A preview that changes only rules takes a fraction of a second; one that changes `include`, `exclude` or `respectGitignore` reads the corpus again, as at startup.
- **Live reload.** Saving a document reloads the pages showing it and keeps the scroll position. A new or deleted document, a folder of documents moved, renamed or deleted, or a change to the config (under any name `--config` gives it) or a `.gitignore`, refreshes the tree on every open page. An image or file appearing or disappearing where a document links reloads that document's pages. A Markdown file the config leaves out changes nothing.

The header stays put when moving between pages: Graph, Dashboard, Changes (in a git work tree) and Config are one segmented control, every page renders the same bar with only the current section chosen, and in browsers with cross-document view transitions the bar and the tree are carried over while only the content between them changes. The tab shows the viewer's own icon.

On a phone the header wraps into three rows — the name with the theme and settings, the sections, the search box — and scrolls away with the page, and the document tree folds behind a **Documents** row above the article, closed on every page so a page opens on its text. Without script the tree stays open.

**Aa** at the right end of the header opens the display settings: the fonts of the whole site — header, tree, side column, panels and dashboard (system, serif, a wide sans, monospace, or any installed font by name) and a monospace font for paths and code — then the article's own text and code fonts, which follow the site's until changed, the text and code sizes, line height, the spacing between letters (code keeps its own), the space between blocks, left or justified text, the article's width or filling the column, the margins on all four sides, and the source line numbers. Each change applies as it is made, and Reset restores the defaults. A phone keeps its own narrow margins.

The theme switch in the header is three segments — Auto (follow the operating system), Light and Dark — chosen with a click or the arrow keys, and the choice is remembered for this address. So are the display settings, applied before the page is drawn so it never shows the defaults first, and the widths of the two side columns, the document tree and the rail with the local graph, outline and backlinks: hovering a column's edge toward the article shows a handle to drag (or focus it and use the arrow keys), a double click on the handle restores that column's default width, and the article always keeps room between them.

## Security

The viewer is bound to `127.0.0.1` unless `--host` says otherwise, writes nothing to the repository unless it was started with `--allow-config-writes`, and outside it writes only review marks, in the state directory. Because any web page in the same browser can make requests to it:

- it answers only requests addressed to localhost, an IP address or the configured host, which defeats DNS rebinding, and refuses requests from other origins;
- it serves documents in the corpus and only the files those documents link to or embed that no `exclude` pattern or `.gitignore` covers, so a request cannot read an arbitrary file by naming it, and a link to a local `.env` does not hand it out; paths that could climb out of the repository are refused before any lookup, and symlinks that lead outside it are not followed;
- raw HTML in Markdown is sanitized with GitHub's allowlist, keeping an author's `name` attribute on links only, where it cannot shadow what the page's scripts read from `document`; every page carries a Content-Security-Policy that allows scripts from the viewer only, and images (SVG included) are served sandboxed;
- a chart option is data: it is parsed as JSON and never evaluated, every tooltip in it is drawn as text, the data view's labels (which ECharts would insert as HTML) are dropped, and a `link` or `sublink` survives only as an `http(s)` URL;
- the config page's preview, save and open, and a review mark, are the only requests with a body. Each must come from the viewer's own page — its origin, a JSON body and a random token only the config page, the Changes page and a changed document's page carry — and a save writes only the config file the corpus was loaded from, inside the repository, over the version the page saw, after the linter's loader has accepted the new text; it is written atomically and read back, and if another program wrote the file in the same moment, that program's version stays and the page says so;
- a review mark is accepted only for the version of a changed document the page showed, and only on a loopback binding, since it records this user's review; it is kept with the text reviewed in the clone's folder of the state directory, which only this user can read, written atomically under a lock every viewer of the clone takes, and a write that fails is reported with the earlier marks left whole. Reading a page creates nothing there;
- opening the config starts the system's own program (Explorer, `open` or `xdg-open`) for that file alone, from an argument list rather than a shell command, and is refused, like saving, when `--host` is not a loopback address, since it would start a program on this machine for someone on another;
- absolute paths appear only on the copy-path button, and only when the viewer is bound to a loopback address, so a viewer reachable from the network does not say where the checkout lives;
- the Changes section, and a document's page to learn whether its document changed, run `git` with an argument list and only to read: it never writes under `.git` — the work tree is compared through `git status`, as a plain `git diff` would refresh and rewrite the index — and it keeps the repository's own git config from starting any program, by turning off its fsmonitor hook, emptying every filter driver and passing `--no-ext-diff --no-textconv`; a `--base` that starts with `-` is refused before git sees it;
- nothing is fetched from the network: Mermaid, ECharts and the page assets come from the installed packages.

## Known limits

- Startup loads and parses the whole corpus, as `wastech-mdlint lint` does: about eight seconds for six hundred documents. After that an edit to a document is applied, re-linted and re-indexed in well under a second; adding or removing a document reloads the corpus.
- The search index is built on the first search (about a second for six hundred documents) and kept in memory.
- The graph is laid out in the browser, every node against every other. Six hundred documents and three thousand links take about a tenth of a second to draw and then settle smoothly; on a corpus many times larger, narrow the graph to a folder.
- The theme, the display settings and the column widths are kept by the browser for the viewer's address. A viewer that starts on another port (the default port was taken, or `--port` differs) opens with the defaults.
- The Changes section notices an edit through the same watcher as the pages, and a commit, a checkout or a fetch on the next request. With `--no-watch` an edit to the work tree shows only after a restart. A Markdown file kept in git-lfs compares as its pointer text, since no filter driver is run.
- The context of a change is computed from both versions of the documents, but two things are read as they are now: a link to a file that is not a document resolves against the files on disk on both sides, since the linter needs a real directory to look in, so a link to a code file the branch deleted reads as fine at the base; and when the config's include, exclude or respectGitignore changed, the base is still read as the documents the current config selects. The Changes page says so when it applies. Linting both versions takes a fraction of a second once per change, kept until the next one; the dashboard's Branch column asks git once per request, as a document's page does.
- In a git work tree a document's page is sent once git has said whether its document changed: usually one short `git` process, and after a save the rebuilt review, a fraction of a second on a branch with a dozen changed documents. A page asked for during that rebuild waits for it rather than starting another. The changed words inside a paragraph are marked only in the Source view and on the Changes page; the rendered page marks whole blocks.
- A review mark covers a whole document, so an edit anywhere in it makes it changed since review, and each path remembers its last ten reviewed versions. Marks are kept under the clone's git directory's location, so a clone moved to another folder, or cloned afresh, starts with none. With **My last review** the diffs compare with the reviewed version, while a card's sizes and findings still compare with the base branch.
- On Linux, Node watches a directory tree with one inotify watch per directory, so a very large `node_modules` inside the repository can exhaust the watch limit. Run with `--no-watch` there, or raise `fs.inotify.max_user_watches`.
