# CTX-003 — Use canonical glossary terms instead of aliases

> Category **CTX** (content) · Scope **project** · Default severity **warning** · Fixable **no** · [Rules index](README.md) · [Configuration](../configuration.md)

## What it checks

Content should refer to a concept by its **canonical term** rather than by a known alias. CTX-003 reads a glossary table, builds an alias → canonical-term map from it, then scans the other in-scope files for alias usage and reports each occurrence.

This keeps a project's vocabulary consistent: if the glossary declares `GraphQL` as canonical with `gql` and `graphql` as aliases, prose that writes `gql` is flagged with a suggestion to use `GraphQL`. Because it correlates a glossary file against the rest of the repository, its scope is **project** (it sees every parsed document at once, not one file in isolation).

Matching is **whole-word**: an alias `api` matches the word `api` but not `APIs` or `myapi`. The glossary file itself is never flagged. An alias identical to the canonical term is ignored.

### How the glossary is read

- `glossary` is a glob selecting the file(s) that hold the glossary table. It is matched against the **scanned corpus**, so a glossary outside `include` (or inside `exclude`) is not read even though it exists on disk.
- In each glossary table, CTX-003 looks for a header named by `termColumn`; tables without that header contribute nothing. The value in that column is the **canonical term**.
- Aliases come from the `aliasColumn` cell, split on commas.
- If the result of all that is **no aliases at all**, the rule cannot check anything and says so — see [When the rule cannot run](#when-the-rule-cannot-run).

### When the rule cannot run

CTX-003 takes a **path** and two **column names**, and any of the three can drift while the config stays valid: rename the glossary file, rename a header, and the rule keeps loading and keeps passing. So when the alias map comes out empty, CTX-003 reports it instead of returning quietly. There are four ways to get there, and the message names which one:

| Cause | What the message says |
| --- | --- |
| `glossary` matched no scanned document | `CTX-003 glossary "nope.md" matched no scanned document, so no aliases were loaded; …` |
| No matched table has a `termColumn` header | `CTX-003 found no table with a "Term" column in glossary "docs/glossary.md", …` |
| `aliasColumn` is omitted | `CTX-003 has no "aliasColumn", so it can never derive an alias to check; …` |
| `aliasColumn` names a header no term table has, or every alias cell is empty | `CTX-003 derived no aliases from glossary "docs/glossary.md": no "Term" table has a non-empty "Aliases" column; …` |

The finding is attributed to the `glossary` value rather than to a file in your corpus — the thing to go and fix is the config — and it is reported at severity **`error`** even though CTX-003 is a `warning` rule by default. That is deliberate: the default `--fail-on` is `error`, so a warning here would print and still exit `0`, which is the silence this exists to end. Because it names a path that is not a document, no inline `wastech-mdlint-disable CTX-003` can suppress it.

Setting `"severity"` on the rule entry still applies to this finding like any other, so `"severity": "warning"` on CTX-003 makes it advisory again. What you cannot get back is no report at all.

## Options

| Option | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `glossary` | `string` (≥1 char) | **yes** | — | Glob selecting the glossary file(s) to read canonical terms and aliases from. |
| `termColumn` | `string` (≥1 char) | **yes** | — | Header name of the column holding the canonical term. |
| `aliasColumn` | `string` (≥1 char) | no | — | Header name of the column holding comma-separated aliases. Optional in the schema, but the rule cannot check anything without it and [reports that](#when-the-rule-cannot-run) rather than passing silently. |
| `section` | `string` | no | — | Only scan content under a heading matching this text; omit to scan whole files. |
| `files` | `string[]` | no | all included | Glob(s) narrowing which files this rule instance scans (the glossary is always excluded from scanning). |
| `exclude` | `string[]` | no | — | Glob(s) removing files from the scan. |

## Example

### Config

```jsonc
{
  "rules": [
    {
      "rule": "CTX-003",
      "options": {
        "glossary": "docs/glossary.md",
        "termColumn": "Term",
        "aliasColumn": "Aliases",
        "files": ["docs/**/*.md"],
      },
    },
  ],
}
```

### Glossary file (`docs/glossary.md`)

```md
| Term    | Aliases      |
| ------- | ------------ |
| GraphQL | graphql, gql |
```

### Fails

```md
We expose a gql endpoint and a graphql schema.
```

→ CTX-003 reports two findings — one for **`gql`** and one for **`graphql`** — each suggesting the canonical term **`GraphQL`**, anchored at the line where the alias appears.

### Scoped to one section

```jsonc
{
  "rule": "CTX-003",
  "options": {
    "glossary": "docs/glossary.md",
    "termColumn": "Term",
    "aliasColumn": "Aliases",
    "section": "Overview",
  },
}
```

Only content beneath an `Overview` heading is scanned for alias usage.

## Notes

- **Scope:** `project` — it reads the glossary and the scanned files together, not one file in isolation.
- The glossary file is always excluded from scanning, so its own alias cells are never flagged.
- Alias matching is whole-word; substrings inside larger identifiers do not match.
- The word boundaries around an alias are only _checked_, not consumed, so repeated aliases are counted independently even when they are back to back: `gql gql gql` reports three findings, not two. The alias itself is also matched literally — punctuation in an alias such as `node.js` has no wildcard meaning.
- With no `aliasColumn`, or when the glossary yields no aliases for any other reason, the rule reports **one `error`-severity finding against the configuration** and skips the alias scan — it does not pass quietly. See [When the rule cannot run](#when-the-rule-cannot-run).
