# FM-001 — Front matter schema

> Category **FM** (front matter) · Scope **document** · Default severity **error** · Fixable **no** · [Rules index](README.md) · [Configuration](../configuration.md)

## What it checks

FM-001 pins the shape of a document's YAML front matter — the block fenced by `---` lines that opens the file. It reports:

- front matter that is **not valid YAML**, or whose top level is not a mapping of keys to values;
- a **required key** that is missing (`required`);
- a value outside an **allowed set** (`allowed`);
- a value that does not match a **pattern** (`patterns`).

With no options at all, FM-001 still checks that every front matter block parses and is a mapping. A broken block is invisible in rendered Markdown, so that check is useful on its own.

A finding about a key (missing, disallowed, mismatched, or holding a mapping) is reported at the block's line range — from the opening fence to the closing fence, because the parsed value carries no per-key positions — and names the key path in its `data.key`. A finding about the block itself has no `data.key`: an invalid-YAML finding is reported at the line where the parser first went wrong, and a non-mapping finding covers the whole block. A missing required key in a document with no front matter is reported for the whole file.

### How values are read

The front matter is parsed once, in the same parse pass as the rest of the document, under YAML's **failsafe** schema: every scalar is a **string** (lists and mappings stay collections), never converted to a number, boolean or date. `version: 1.10` is the string `1.10` (not the number `1.1`), `draft: yes` is the string `yes`, `date: 2026-01-01` is the string `2026-01-01`, and an empty value (`owner:`) is the empty string. Allowed values and patterns are compared against that parsed string. That is not always the literal text in the file, because YAML's own string syntax is applied first: a plain value written across several lines is folded into one line, quotes are removed and escapes decoded (`"x\u0041"` is `xA`, `'it''s'` is `it's`), and a block scalar (`|` or `>`) is joined or folded and keeps its final line break, so `status: |` followed by an indented `accepted` is `accepted` plus a newline and does not equal `accepted`; write `|-` or `>-` to drop that line break. The trade-off is that `true` and `"true"` cannot be told apart, which does not matter for string checks.

- **Key paths** use dots to reach into nested mappings: `owner.team` reads `team` inside `owner`. A key whose own name contains a dot cannot be addressed.
- **Lists are checked item by item.** For `tags: [api, web]`, each of `api` and `web` must be allowed (or match the pattern); each offending item is its own finding.
- **A mapping value** for a key under `allowed` or `patterns` is reported once, since no string check can judge it.
- **An absent key** is only reported when it is listed in `required`. `allowed` and `patterns` skip a document that lacks the key.

### Invalid front matter is one finding

A block that is not valid YAML, or whose top level is a list or a plain string instead of a mapping, yields **exactly one** FM-001 finding, however many checks are configured, and the run carries on. Its values are not checked, because a value the parser could not read is not something a schema can judge.

The parser is strict about anything it would otherwise have to guess at, and treats each of these as invalid:

- a duplicate key;
- a tag (`!something`, `!!int`, `!!js/function`): no tag is ever constructed or executed;
- more than one YAML document in the block;
- a list or mapping used as a key;
- alias expansion beyond a fixed bound, so a small block cannot expand into an enormous value.

The YAML merge key `<<` is **not** special: it is an ordinary key, so a block cannot pull keys in from elsewhere.

### Documents without front matter

A document with no front matter is reported **only** when `required` lists keys: one finding per missing key, reported for the whole file (no line number). With only `allowed` or `patterns` configured, a document without front matter passes. Use `files` / `exclude` to limit `required` to the document families that must carry front matter.

## Options

| Option | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `required` | `string[]` | no | — | Key paths that must be present. |
| `allowed` | `{ [keyPath]: string[] }` (each ≥1) | no | — | For each key path, the values it may hold. Compared exactly (case-sensitive). |
| `patterns` | `{ [keyPath]: string }` | no | — | For each key path, a regex its value must match. Validated at config load. |
| `files` | `string[]` | no | all included | Glob(s) narrowing which files this rule instance applies to. |
| `exclude` | `string[]` | no | — | Glob(s) removing files from this rule instance. |

`patterns` takes a bare regex string with no separate flags field, so the common case stays one line per key. For case-insensitive matching, use the inline modifier group `(?i:…)`, for example `"^(?i:adr)-\\d+$"`. The [`frontmatterMatches`](custom.md#assertion-kinds) custom kind accepts a `flags` field if you need one.

## Example

### Config

```jsonc
{
  "rules": [
    {
      "rule": "FM-001",
      "options": {
        "files": ["docs/adr/**/*.md"],
        "required": ["status", "owner.team"],
        "allowed": { "status": ["proposed", "accepted", "superseded"] },
        "patterns": { "id": "^ADR-\\d{4}$" },
      },
    },
  ],
}
```

### Passes

```md
---
id: ADR-0007
status: accepted
owner:
  team: platform
---

# Use one parse pass
```

### Fails

```md
---
id: adr-7
status: done
---

# Use one parse pass
```

→ FM-001 reports three findings at lines 1–4: the required key **`owner.team`** is missing, the value **`done`** for **`status`** is not one of `proposed, accepted, superseded`, and the value **`adr-7`** for **`id`** does not match `^ADR-\d{4}$`.

```md
---
status: [accepted
---
```

→ FM-001 reports one finding: the front matter is not valid YAML. No key check runs on that document.

## Notes

- **Scope:** `document` — evaluated per file, independent of other files.
- **Reserved prefix.** `FM` is a built-in category, so a [`custom`](custom.md) rule id may not start with `FM-`. A config whose custom rule was already named `FM-…` fails to load and needs a new id.
- **Per-family schemas.** FM-001 can be listed several times with different `files` scopes, one schema per document family. To run the same checks under your own rule id, use the `frontmatterRequired`, `frontmatterInSet` and `frontmatterMatches` kinds of the [`custom`](custom.md) rule, which share these semantics.
