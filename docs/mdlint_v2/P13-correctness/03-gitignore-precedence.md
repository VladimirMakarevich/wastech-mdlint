# P13.03 · `.gitignore` layer precedence is root-first-wins

> Phase: [P13 — Correctness](index.md) · Roadmap: [v2 Index](../index.md) · Size **S–M** · Status **Done**. Backlog: [W-11](../remediation-backlog-2026-08-05.md) (Medium). Sources: audit F9 (MEDIUM; reproduced against real `git` in the audit and again in its QA pass). Depends on [P12](../P12-consistency/index.md).

## Goal

Make `respectGitignore: true` mean what its name says: the corpus matches what `git` actually tracks, including when a nested `.gitignore` re-includes a file a root pattern excluded.

## Problem

[`packages/core/src/discovery/gitignore-layers.ts`](../../../packages/core/src/discovery/gitignore-layers.ts) around `:42` iterates layers from the repository root downward and returns `true` at the first layer that ignores. Git's rule is the opposite: the **deeper** `.gitignore` takes precedence, so a nested `!keep.md` cannot re-include a file a root pattern ignored.

The failure direction is **under-reporting** — the linter silently drops a file real `git` keeps. Reproduced against real `git`: with root `*.md` and `docs/.gitignore` holding `!keep.md`, `git check-ignore -q docs/keep.md` exits `1` (not ignored) and `git status --ignored` lists only `docs/other.md`, while the linter's corpus was empty. Moving the negation into the root file made both agree.

**One implementation, two consumers, consistently wrong together.** The shared matcher is stated as such at `gitignore-layers.ts:6`, and `isGitIgnored` has exactly two call sites — the corpus walk and `init`'s pre-config scan. That is the good news: there is one place to fix. The within-file half of git's semantics **is** correct, which is exactly what [`glossary.md`](../glossary.md) carefully claims and no more.

**The field test is not counter-evidence.** It reported `respectGitignore` as honoring nested `.gitignore` files perfectly — but its target's five nested negations were all `.vscode/*.json` and `/build/.npmkeep`, no Markdown, so the re-inclusion case was never presented. A clean bill on a case the corpus does not contain is not a passing test.

## Deliverables / steps

1. **Evaluate layers deepest-first and stop at the first layer with an opinion.** This needs the `ignore` package's three-state `test()` (which distinguishes "ignored", "unignored", and "no opinion") rather than the boolean `ignores()` currently used — so it is deliberately **not** a one-line change, and the task is sized accordingly.
2. **Keep the single-matcher property.** Both call sites must continue to share one implementation; do not fix the corpus walk and leave `init`'s scan on the old semantics, or `init` will write a config that disagrees with the linter that reads it.
3. **Fixture, in both directions.** A nested Markdown re-inclusion must agree with `git check-ignore`, and so must the case where a nested pattern _adds_ an ignore the root did not have. Assert against real `git` output rather than against a hand-written expectation, so the fixture stays honest if `git`'s behavior is ever misremembered.
4. **Documentation.** `docs/guide/configuration.md:48` currently sells `respectGitignore` with no caveat. Either this fix removes the need for one, or the residual caveat lands there — not in a task file.
5. **Glossary.** The `respectGitignore` entry describes the loader default and `init`'s behavior; extend it with the layer-precedence rule now that it is a stated contract rather than an accident.

## Out of scope

Making `respectGitignore` default to `true` — that decision belongs to [P13.02](02-default-exclude.md), which owns the defaults. Note the dependency runs the other way for that half: P13.02 must not flip the default on until this task has landed, or the precedence bug reaches the zero-config path. Supporting `.git/info/exclude` or a global core.excludesFile: neither is claimed anywhere, and adding them would widen the contract this task exists to make honest.

## Exit criteria

- [x] A fixture with a nested Markdown re-inclusion agrees with `git check-ignore` in both directions.
- [x] A nested pattern that adds an ignore still works — the fix must not invert into over-inclusion.
- [x] Both call sites (corpus walk, `init` scan) go through the same matcher, asserted rather than assumed.
- [x] `docs/guide/configuration.md` either needs no caveat or states the one that remains.
- [x] The glossary's `respectGitignore` entry states the precedence rule.
- [x] Gates green.

## Implementation notes

- **The reversal plus three-state testing is the fix for _files_; the ancestor rule needed its own half.** `isGitIgnored` iterates `layers` from the last index down and returns at the first layer whose `Ignore.test()` reports `ignored` or `unignored`, falling through when it reports neither. The path-to-layer arithmetic moved into a named `relativeToLayer` helper so the loop body is just the precedence rule; its `undefined` return also documents why the "nothing left to test" case must be filtered rather than passed on — `ignore`'s `test("")` **throws** (`path must not be empty`), verified directly against `ignore@7.0.5`, so that guard is load-bearing, not defensive.
- **The reversal alone still disagreed with git on a subtree re-inclusion, because one layer cannot answer the ancestor question.** `Ignore.test()` resolves a path's parents against _its own_ rules and then honors git's "cannot re-include under an excluded parent" within that one rule set (`ignore@7.0.5`, `index.js`, `Ignore._t`: `return cache[path] = parent.ignored ? parent : this._testOne(path, …)`). Across layers that is wrong: with root `artifacts/*` and `artifacts/.gitignore` holding `!docs/`, real `git` **keeps** `artifacts/docs/one.md` — `artifacts/*` does not cross `/`, so nothing matches the file itself — but the root layer reported the file as ignored because it re-applied its own exclusion of `artifacts/docs` to the file's parent, a directory the deeper layer had already re-included. Probed against `git` 2.51.0, not reasoned about: `git ls-files --others --exclude-standard` lists the file and `git check-ignore --no-index` exits `1` for it. The same divergence appeared with root `docs/generated/` + `docs/.gitignore` holding `!generated/`, and it also made the two verdicts inconsistent with each other — `isGitIgnored` said "descend" for the directory and "drop" for every file inside it.
- **So `isGitIgnored` owns both halves of git's rule now.** It resolves each ancestor prefix across _all_ layers first (deepest-first per prefix, outermost prefix first) and returns `true` at the first ancestor that resolves to ignored; only if none does, the path's own verdict decides. Each layer is then asked with its inherited ancestor exclusions suppressed, via a cached copy built as `ignore().add(layer.ig).add(negations)` — the `Ignore` overload of `add` is public and typed. The negations are one slash-anchored, directory-only wildcard per ancestor level (`/*/`, `/*/*/`, …), so they cancel exactly the query's strict ancestors, can never match the query itself, and win under gitignore's last-match-wins. **Expressing them by depth rather than by name is the load-bearing choice**: splicing the actual directory names into pattern text would read a directory called `we[i]rd` as a character class and silently restore the bug, which is why there is a fixture for exactly that name. The copies are memoized in a `WeakMap` keyed by layer and depth, so a walk builds at most one per layer per depth and nothing outlives the walk.
- **Validated as a matcher, not just as a fixture.** The algorithm was checked against real `git` on 26 fixture trees — every file _and_ every directory in each, compared with `git check-ignore --no-index --stdin`: the two subtree shapes above, the within-file and cross-file negation shapes, `*`-excludes-everything, `**` patterns, anchored deep patterns, a re-included directory whose own subdirectory is excluded again, three- and four-level layer chains, and directory names holding `[`, `]`, `#`, spaces, and non-ASCII characters. Zero mismatches — within what those oracles can see. No fixture presents a path differing from its pattern only in **case**, and none could settle it: our matcher is case-insensitive (the `ignore` default), while `git`'s answer depends on `core.ignoreCase`, which is `true` on macOS. That divergence predates this task and is outside W-11, so it is recorded in the [accepted behaviors register](../accepted-behaviors.md) and the guide caveat rather than left to be re-found. On the first 12 of those trees, where the pre-fix matcher was run alongside, it mismatched on 11 paths across 7 of them — in both directions: files git keeps that it dropped, and one file git ignores that it kept. Throughput cost is roughly 2× per query at depth 6 with four layers (~20 µs), which is far below the per-file parse it precedes.
- **The array's order became a stated contract.** Both walks already appended each directory's layer as they descended, so they arrive outermost-first; reversing that array _is_ the precedence rule. That is now in `IgnoreLayer`'s doc comment and pinned by a test that feeds the same two layers in both orders and asserts the verdict flips.
- **Two `git` oracles, and the reason for the second turned out not to hold.** The design anticipated that `git check-ignore` would not consider an _ancestor_ directory's exclusion — which would have made it useless for the "cannot re-include under an excluded parent" fixture and forced a second oracle. Probed against `git` 2.51.0 instead of assumed: `git check-ignore --no-index generated/x.md` **does** report `.gitignore:1:generated/` as the deciding pattern, at arbitrary depth. So every fixture is compared against both oracles. The pair is still worth keeping: `ls-files --others --exclude-standard` is git's own traversal and answers "what is the corpus", while `check-ignore --stdin -z` answers the per-path question the exit criterion names, and agreement between two independently derived answers is stronger than either alone. Both helpers throw on an unexpected exit status, so a broken invocation can never read as "not ignored".
- **`--no-index` is the semantically correct flag, not a convenience.** Index-aware `check-ignore` reports a tracked file matching an ignore pattern as _not_ ignored (confirmed: `git check-ignore tracked.md` exits `1` while `--no-index` exits `0`), because a `.gitignore` never un-tracks anything. Our matcher is pattern-only and has no index, so `--no-index` is the oracle that answers the same question. That difference is the one residual, and it is now a user-facing caveat in `docs/guide/configuration.md` plus a row in the [accepted behaviors register](../accepted-behaviors.md) rather than a silent gap.
- **The single-matcher criterion is asserted twice, structurally and behaviorally.** Structurally: each call site's source must import `gitignore-layers.js`, call `isGitIgnored(`, and _not_ import `ignore` directly — plus a walk of every workspace package's `src` that pins the consumer set to exactly those two files and the matcher's own module, so a third call site cannot appear untested. That package list is read from the workspace (the root `workspaces` value is asserted to still be `["packages/*"]`, and a member without a `src` is skipped) rather than hardcoded, so a fourth package is scanned the day it exists instead of being silently unscanned by a test that claims to pin the whole set. Behaviorally: `scanRepository` over the layer-precedence fixture must sample exactly the set `git ls-files` keeps.
- **The new tests were verified red before the fix, against both pre-fix shapes.** Restoring the original root-first loop with the boolean `ignores()` turns 11 of the 22 new cases red; the fix turns all 22 green. Restoring only the intermediate deepest-first loop — the reversal without the ancestor half — still leaves 5 of them red (the three ancestor unit cases, the subtree oracle fixture, and the loader's subtree corpus case), which is what pins the second half as load-bearing rather than defensive. No pre-existing case moved in either direction: the four fixtures the plan flagged as at-risk (`load-documents.test.ts`'s `.gitignore` case and `repo-scan.test.ts`'s three gitignore cases) stayed green unchanged, as expected — `ignores()` and `test().ignored` differ only in `checkUnignored`, which changes `unignored` (the new signal) and never `ignored`.
- **`git` presence _and version_ gate only the oracle block** (`describe.skipIf`). The floor is `git >= 2.32`, parsed from the same `git --version` probe, because that block has two implicit version dependencies: neutralizing a developer's global `core.excludesFile` relies on `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` pointed at absent paths reading as empty, and the per-path oracle relies on `check-ignore` naming an ancestor directory's pattern. On an older toolchain a contributor gets a skip rather than an assertion diff caused by their own global config leaking into the fixture. The unit block covers both halves of the rule with no `git` on PATH at all, and `load-documents.test.ts` / `repo-scan.test.ts` gained git-free cases for the cross-layer shapes their existing fixtures never presented — the file shape in both, plus the subtree shape in the loader, whose corpus is where "descend, then drop everything inside" was visible (the repo-scan fixtures were single-layer, both the ignore and its negation in one file, so neither could have caught this).
- **No public surface moved.** `gitignore-layers.ts` is not re-exported from `packages/core/src/index.ts`, and no rule metadata, option schema, or config key changed, so `packages/cli/schema.json` and the generated README tables are byte-identical and the `docs-sync` / `schema-generation` tests did not move. No new runtime dependency: `ignore@7.0.5`'s three-state `test()` was already there behind the boolean wrapper.
- **`respectGitignore`'s default is untouched** (`false`), per this task's out-of-scope list — [P13.02](02-default-exclude.md) owns that flip and is now unblocked.
