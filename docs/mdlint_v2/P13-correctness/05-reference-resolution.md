# P13.05 · Reference and extension resolution

> Phase: [P13 — Correctness](index.md) · Roadmap: [v2 Index](../index.md) · Size **M** · Status **Done**. Backlog: [W-08](../remediation-backlog-2026-08-05.md) (High), [W-09](../remediation-backlog-2026-08-05.md) (Medium), [W-10](../remediation-backlog-2026-08-05.md) (Low). Sources: audit F4 (MED-HIGH, reproduced twice), F8 (MEDIUM, reproduced), F15 (MEDIUM there, downgraded to Low per the QA pass). Depends on [P12](../P12-consistency/index.md).

## Goal

Make reference resolution answer one question one way: a documented `exclude` must apply on every branch, and "a Markdown file" must mean the same thing to the coverage signal, the `init` scanner, and the default `include`.

## Problem

**W-08 — `REF-001.exclude` goes inert whenever any `siteRouter` is set.** [`packages/core/src/engine/primitives/reference.ts`](../../../packages/core/src/engine/primitives/reference.ts) splits resolution into two branches at `:70` and applies `options.exclude` on only one of them (`:88`). The image sibling has no split and always applies it — so one broken primitive, not two.

**The trigger is cheaper than it looks.** Every `siteRouter` field is optional and the object is strict, so a bare `{}` validates; with no preset the router returns the stripped path, behaviorally identical to the no-router branch **except** that `exclude` stops applying. Reproduced twice, identically: same fixture, `exclude: ["generated/**"]` and no router exits `0`; adding `"settings": {"siteRouter": {}}` and changing nothing else reports the link and exits `1`.

**Second caller, and the guide pairs the two options itself.** The declarative-custom-rule dispatcher passes a user's `assert.exclude` straight into `linkResolves` ([`primitives/assert.ts`](../../../packages/core/src/engine/primitives/assert.ts) `:233`), so a `custom` rule inherits the hole — the family where the option is most likely hand-written. And `docs/guide/config-reference.md` sets a whole-config `starlight` router, notes most projects set it exactly once there, and then shows a `REF-001` entry combining `exclude` with a per-rule router: a reader gets the inert combination by following the guide, not by misusing it.

**W-09 — three incompatible definitions of "a Markdown file".** Coverage uses `.md` + `.markdown` ([`graph/coverage.ts`](../../../packages/core/src/graph/coverage.ts) `:32`); `init`'s scanner uses `.md` + `.mdx` ([`discovery/repo-scan.ts`](../../../packages/core/src/discovery/repo-scan.ts) `:55`); the default `include` is the `.md` glob alone ([`engine/lint-files.ts`](../../../packages/core/src/engine/lint-files.ts) `:75`). `.markdown` appears nowhere else in core and on no guide page. So the coverage signal — whose entire job is naming on-disk Markdown that is linked-to but outside the corpus — checks for an extension no default configuration can admit, and is blind to the one `init` exists to find. Reproduced: `filesOutsideCorpus` listed `docs/legacy.markdown` and never mentioned `docs/page.mdx`.

**W-10 — two disagreeing image-target resolvers.** Router-aware in [`graph/build-context-graph.ts`](../../../packages/core/src/graph/build-context-graph.ts) `:20` and `coverage.ts:86`; router-blind in `reference.ts:129` and in `init`'s REF-003 tally at [`discovery/rule-inference.ts`](../../../packages/core/src/discovery/rule-inference.ts) `:114`, whose comment claims it mirrors the rule. The graph builder's invariant comment says resolution mirrors the REF rules "so graph edges never disagree with the REF rules"; it names REF-001 and REF-002, so it is literally accurate, but the same helper carries images. **The behavioral effect was never measured** — the QA pass confirmed the structure and noted this, which is why it is Low: a router-routed candidate ends in a Markdown extension and an image rarely does.

Whatever is chosen, `docs/guide/context-graph.md:31` advertises coverage with no extension caveat and must end up true.
5. **W-10 — either direction is acceptable, but pick one:** route images through the shared candidate helper, **or** narrow the graph builder's invariant comment to say images are deliberately excluded. Do not leave one model claimed and two implemented.
6. **Glossary.** The **REF** family entry and the coverage/`filesOutsideCorpus` entries describe these behaviors; update what changes.

## Out of scope

Making `.mdx` a first-class linted extension — that is a product decision with parser implications, and nothing in the backlog asks for it. This task's obligation is that the three sites agree and that the guide describes the agreement.

## Implementation notes

- **W-08 was not a patch onto the router branch; it was deleting the branch.** `resolveTargetCandidates` (`engine/path-resolve.ts`, P4.06) already reproduces all three of `linkResolves`'s cases exactly — relative → source dir, root-relative + router → `resolveRoutedUrl` + `normalizeRelativePath`, root-relative without one → strip + normalize — so both primitives now build one candidate list and pass it through one `exclude` gate. Adding the missing `matchesConfigGlob` call to the second branch would have left two code paths that must agree; converging removes the shape the defect lived in. Deliverable 1 named the narrower fix, which is why this is called out rather than assumed equivalent.
- **The gate is `some`, not a filter.** `exclude` is a suppression filter and must never _create_ a finding, so a match on **any** candidate skips the target. Filtering matched candidates out and re-resolving the rest would report a link that resolves only via an excluded candidate — a new false positive introduced by the fix. With one candidate, which is every non-router case, `some` is byte-identical to the old behavior. The whole list still reaches `matchesConfigGlob` in one call, since it is [P13.01](01-glob-semantics.md)'s ordered, negation-aware matcher.
- **One primitive change closed both callers, and the custom half is what proves it.** The declarative dispatcher (`primitives/assert.ts`) hands `assert.exclude` straight to `linkResolves`, so the same edit fixes `REF-001` and a `custom` rule. That half had no test at all before this task; it now has one that fails against the pre-fix source, which is the only cheap evidence that the two callers really are one primitive.
- **Drift in the problem statement, no behavior consequence.** The task and the backlog cite the default `include` at `engine/lint-files.ts:75`. [P13.02](02-default-exclude.md) moved it: it is `DEFAULT_INCLUDE_GLOBS` in `config/corpus-scope.ts`, and `lint-files.ts` now just calls `resolveCorpusScope`. Same fact, different file — the W-09 edit landed in `corpus-scope.ts`.
- **W-09's set is `.md` + `.mdx`, with the linted subset declared rather than described.** `discovery/markdown-extensions.ts` exports `MARKDOWN_EXTENSIONS` (on disk), `LINTED_MARKDOWN_EXTENSIONS` as a subset of it, `MARKDOWN_GLOB_SUFFIX` derived from the former, and `isMarkdownFile`. `DEFAULT_INCLUDE_GLOBS` is now derived from the subset — byte-identical output today, and the out-of-scope guard ("`.mdx` is not linted") becomes a structural relation instead of a comment two files away. `.markdown` is dropped: it existed only in coverage's local helper, nowhere else in core and on no guide page, so it could never lead anywhere a default `include` would follow. That narrowing is the one thing this task takes away from a user, so it is stated on the coverage guide page and in the [register](../accepted-behaviors.md) rather than left silent. `isMarkdownFile` uses `path.posix.extname`, which serves both a bare `Dirent.name` and a repo-relative candidate — and makes a file named exactly `.md` a non-match, unlike coverage's old `endsWith`.
- **W-10 resolved toward router-blind, because that is the model the rule page already documented.** `REF-003.md` states that root-relative image targets resolve against the repository root, so the claim that was wrong was the graph builder's invariant comment, not the rule's. Routing images would have been actively harmful: under `starlight`, `resolveRoutedUrl("/img/logo.png")` offers only `src/content/docs/img/logo.png.md`-shaped candidates, so an asset would be probed as Markdown source and REF-003 false positives manufactured. The builder and `coverage.ts` now pass `undefined` for the router on images; coverage's `collectRawTargets` had to stop flattening kinds to do it, and returns `{ target, routable }` instead. Behavioral delta is near zero — a root-relative image whose candidates are all Markdown could rarely be a real node — which is why the audit downgraded it to Low, and why the two new tests are openly contrived: an image target only distinguishes the two models when the router maps it onto a real Markdown file. Both were checked red against the routed implementation, so they pin the choice rather than merely passing beside it.
- **`rule-inference.ts`'s comment was accurate but over-readable.** It claimed to mirror `imageResolves`; it mirrors that primitive's _skip guards_ (empty target, scheme-qualified target) and never resolves anything. Tightened to say so, which is a five-word change rather than a fix.
- **Verified at the process boundary, by hand, through the built CLI.** `exclude: ["generated/**"]` over `docs/a.md` → `[gen](/generated/x.md)`: exit `0` with no router, exit `0` with `"settings": {"siteRouter": {}}`, exit `0` with a per-rule `{}`. Separately, `config-reference.md`'s combined example was run as written — `"exclude": ["**/CHANGELOG.md"]` beside a whole-config `starlight` router — and skips both a routed `/CHANGELOG` and a relative `../CHANGELOG.md` while still reporting an unrelated missing target, so the guide's "skips links _to_ any CHANGELOG.md, from anywhere" is now true rather than aspirational.
- **One residual recorded, not fixed.** With a router whose `preset` is unknown (a bare `{}` included), `resolveRoutedUrl` returns the stripped URL un-normalized, so `/gen/../generated/x.md` yields the candidate `gen/../generated/x.md` where the no-router branch yields `generated/x.md`. `existsSync` still resolves it, but an `exclude` glob written against the normalized path will not match. Real, narrow, pre-existing, and outside W-08 — `resolveTargetCandidates` is read by three subsystems, so normalizing that branch is a shared-behavior change that wants its own task. It is in the [register](../accepted-behaviors.md).
- **Nothing here touched a rule's options schema**, so `packages/cli/schema.json` and the README rule table regenerate byte-identical — confirmed by running `generate:docs`, not assumed.
