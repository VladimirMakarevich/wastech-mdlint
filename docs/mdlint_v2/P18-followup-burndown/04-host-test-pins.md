# P18.04 — Host and packaging pins, and three stale test names

> Phase: [P18 — Follow-up burn-down](index.md) · Roadmap: [v2 Index](../index.md) · Size **M** · Status **Done**. Depends on [P18.02](02-code-fixes.md) (FU-24 pins a branch that task also touches).
>
> Eleven items in the CLI, core and MCP test suites. Four were missing coverage, four were guards weaker than they read, three were names or titles describing a contract that has moved.

## What was wrong, and what was done

- [x] **FU-24 — the `ENOTDIR` branch had no test.** In `resolveToolCwd`'s `stat(resolved).catch(...)` handler, the existing "exists but is a file" case passes the file itself, which `stat`s successfully and is caught by `!stats.isDirectory()` — so the rejection handler's own branch was never entered. A path _under_ a file is the only shape that makes `stat` fail with a non-`ENOENT` errno, and it is what a client hits by joining a subdirectory onto a path that turned out to be a file. `packages/mcp-server/test/tool-context.test.ts` now writes a file and calls `resolveToolCwd({ cwd: path.join(filePath, "sub") })`, asserting code, hint and the path through the `posix()` helper [P18.02](02-code-fixes.md) added. Code/hint/path only, deliberately: POSIX reports `ENOTDIR` and Windows `ENOENT`, and both branches have to satisfy the one assertion.
- [x] **FU-25 — two host-parity guards were untagged and their file uninventoried.** `packages/cli/test/graph.e2e.test.ts` holds both the new nested-coverage parity test and the widened top-level one, each matching the `host-parity` definition exactly, but the file appeared in neither `BOUNDARY_GUARDS["host-parity"]` nor the `host-parity` row of [.agents/rules/testing.md](../../../.agents/rules/testing.md) — so deleting them failed nothing, the drift the inventory exists to catch and a miss against [P16.01](../P16-release-readiness/01-test-debt.md)'s "every boundary guard is tagged". Now tagged and inventoried in both places. **The renderer-level twin in `packages/core/test/graph-render.test.ts` stays untagged on purpose**, and the tag comment says so: it compares two functions, not what a host hands a reader, and this category is about the process boundary.
- [x] **FU-26 — a step-order guard read the whole module including comments.** The guard in `packages/mcp-server/test/lint.test.ts` asserted `source.includes(step)` is `false` for `parseDocument`, `runRules` and `createSuppressionChecker` against the full file text, so a future comment naming any of the three would fail the suite with a message reading like a step-order regression — which is why the handler's current comment paraphrases them. The haystack is now the module's import statements alone, which is what the guard was ever about; `expect(…).toContain("lintContent")` moved with it.
- [x] **FU-27 — a test title named a superseded four-key contract.** `packages/cli/test/cli.test.ts`'s graph-JSON test still named `{ nodes, edges, components, readingOrder }`, six keys since [P15.02](../P15-output-contracts/02-graph-output-contract.md) unified that list across five documentation surfaces — the same drift one layer down. Renamed to the shipped six. No body change: the exhaustive pin lives in `packages/core/test/graph-render.test.ts`.
- [x] **FU-28 — the completion-surface `STATUS` regex was not anchored.** `/Status \*\*([^*]+)\*\*/` matched the first occurrence anywhere in a file, prose included, and three plan files quote a status in prose — one of them quoting `Status **Done**` while its own header reads `Not started`. Green today only because every header comes first; a file that lost its header status would silently inherit a prose one, defeating the "declares a status on every index and task file" assertion and able to flip a derived index status without failing anything. Now `/^> .*Status \*\*([^*]+)\*\*/m`, which every plan file's header line satisfies and no prose mention does.
- [x] **FU-29 — the doc-URL guard pinned only the path half.** The "resolves to a real page" test stripped `RULE_DOCS_BASE_URL` and checked the filename on disk, leaving the owner/repo/branch half unpinned — and that half is a second spelling of the root `package.json`'s `repository.url`, so a rename that updated the manifest and missed the constant would turn every finding's `helpUri` and all 24 README table links into 404s with the suite green. `packages/core/test/registry-inventory.test.ts` now derives the origin from the manifest, with the same repo-root derivation it already used for `RULE_DOCS_DIR`, and asserts the constant is built against it.
- [x] **FU-30 — `readTarball` was untested binary parsing.** `packages/core/test/support/read-tarball.ts` is ~90 lines of hand-rolled ustar parsing, exercised only indirectly, and its dangerous failure is a **partial** map: a mid-walk header misread drops every later entry, each of which surfaces in `package-payload.test.ts` as `"<pkg> ships no <entry>"` — the reader's bug reported as a packaging defect, where that suite's positive control only ever sees a fully empty map. The new `packages/core/test/read-tarball.test.ts` assembles archives in memory dependency-free (512-byte headers written by hand plus `gzipSync`) and pins: a directory entry, a pax header and an unpadded body all stepped over with the ordinary entry _after_ them still read; `prefix` + `/` + `name` joined for a split long path; the leading `package/` stripped; and a non-octal size field throwing rather than returning a truncated map. Each case puts an ordinary file last, because arriving at it is what proves the walk stayed aligned.
- [x] **FU-31 — cleanup could mask the real failure.** `afterAll` in `packages/core/test/package-payload.test.ts` ran `rm(packDir, …)` unconditionally, but `packDir` is assigned by the first statement of `beforeAll`; an `mkdtemp` that failed left it `undefined` and `rm` threw a `TypeError` over the error that mattered. Guarded, and the declaration widened to `string | undefined` so the guard is not a comparison the type rules out.
- [x] **FU-32 — eighteen published README links resolved to nothing on disk.** The three package READMEs carry absolute `blob/main/<path>` links to guide pages and to each other. Being absolute is what makes them work on the npm page and also what makes the REF rules skip them, so a renamed guide page rots them silently — on the surface [P16.02](../P16-release-readiness/02-package-metadata.md) exists to make readable. `package-payload.test.ts` now scans each **packed** README for those links and resolves each path back to the repository, reusing `RULE_DOCS_BASE_URL`'s repository prefix rather than re-spelling the URL, with a non-vacuity check so a README that lost every link cannot pass. `registry-inventory.test.ts` already guarded this class for rule doc pages.
- [x] **FU-33 — a derivation keyed on a metavar could silently drop a handler.** `commandsAcceptingConfig()` probed each command's help for the literal `"--config <file>"`, so a future command declared `--config <path>` would fall out of the derived set, the equality assertion against the hand-written `ROWS` would still pass, and the new handler would never be parametrized — the silent uncoverage [P14.04](../P14-host-boundary/04-config-resolution-base.md)'s criterion 6 exists to prevent. Now `/--config\b/`, verified safe (no other command's help text carries the token). The comment also records what this derivation structurally cannot do: root help hides hidden commands, so a future hidden one taking `--config` has to be added to `ROWS` by hand.
- [x] **FU-75 — one describe title was a prefix of another.** The standalone `schema.json` suite in `package-payload.test.ts` is no longer byte-identical to the `(W-29)`-suffixed title `describe.each` generates for the same package, so a failure is already attributable — but a prefix still cannot be selected alone with `-t`. Renamed to state its subject: `published payload of @wastech-mdlint/cli — allowlist-only files (W-29)`.

## Notes

**None of these eleven turned out to be a registered decision.** Each was checked against [accepted-behaviors.md](../accepted-behaviors.md) and the owning phase's implementation notes first, per the standing lesson of this phase; the register's only nearby row is the `helpUri` `blob/main` one, which is about _which branch_ the URL names and is untouched by FU-29 pinning _which repository_ it names.

**One documentation surface moved with the code:** the `host-parity` row of [.agents/rules/testing.md](../../../.agents/rules/testing.md) gained `packages/cli/test/graph.e2e.test.ts`, in the same change as the inventory — the pairing that table's own rules call discipline rather than enforcement, since the inventory does not parse it.

**FU-32 found no dead link.** All eighteen targets resolve today; the guard is what keeps that true through the next rename, which is the point — the defect it prevents is only visible after publishing.
