# P14.04 · `--config` resolves against two different bases

> Phase: [P14 — Host boundary](index.md) · Roadmap: [v2 Index](../index.md) · Size **S–M** · Status **Done**. Backlog: [W-16](../remediation-backlog-2026-08-05.md) (Medium). Sources: audit F10 (MEDIUM, reproduced). Depends on [P13.06](../P13-correctness/06-config-diagnostics.md), and — if direction (A) is chosen — on [P14.01](01-mcp-cwd-validation.md), which refactors the same MCP `cwd` resolver.

## Goal

Make `--config` mean one thing across all six handlers that accept it, or state the divergence in the two places the repository's own rules say a deferral must live.

## Problem

`loadConfiguration` resolves an explicit config path against the **process** working directory, ignoring its own `cwd` parameter ([`packages/core/src/config/load-config.ts`](../../../packages/core/src/config/load-config.ts) around `:182`, `path.resolve(params.explicitConfigPath)` with no `params.cwd`). Four CLI handlers inherit that — `lint`, `graph`, `slice`, `impact` — while `compile` and the MCP context helper work around it locally. The hazard is written down at [`packages/cli/src/commands.ts`](../../../packages/cli/src/commands.ts) `:422`: "`loadConfiguration` resolves `explicitConfigPath` against `process.cwd()`, which silently diverges from `command.cwd` when the two differ."

**User-visible, reproduced:** from a directory containing `proj/cfg.json`, `lint proj --config cfg.json` prints `Config file not found: ../cfg.json` — a path the user never typed, rendered relative to the lint root while resolved against the shell. `compile --cwd proj --config cfg.json` finds the same file.

**The deferral is recorded in the wrong place.** It currently lives only in a task file (`P11-remediation/10-cli-exit-contract.md:47`), which violates the repository's own same-change register rule: a behavior accepted rather than fixed belongs in [`accepted-behaviors.md`](../accepted-behaviors.md) with a user-facing home, not in the prose of a task nobody re-reads.

## Deliverables / steps

1. **Decide the direction.**
   - **(A) Honor the caller's `cwd`** in `loadConfiguration` for all six call sites, and delete the two local workarounds. This is the behavior the guide implies and the one that removes a divergence rather than documenting it.
   - **(B) Keep process-cwd resolution**, add the register row, and state the base at `docs/guide/cli.md:43` where `--config` is documented.
2. **If (A), the diagnostic path matters as much as the resolution.** The reproduced symptom is two bugs compounding: the path resolved against one base and _rendered_ relative to another. Fixing resolution without fixing rendering leaves a correct lookup reported against the wrong base. [P13.06](../P13-correctness/06-config-diagnostics.md) settles the notation question for config diagnostics; keep this consistent with whatever it chose.
3. **If (A), land after [P14.01](01-mcp-cwd-validation.md).** The workaround there is one of the four `cwd` sites P14.01 touches, and P14.01's own first deliverable is to make that resolver the single entry point — so removing the workaround first would leave the resolver half-refactored. Direction (B) touches no MCP code and carries no such ordering.
4. **Either way, remove the task-file-only deferral.** If (A), it is obsolete and should be marked so. If (B), it moves to the register.
5. **Test the six handlers together**, not one: the finding is an inconsistency across call sites, so a test that pins only `lint` would pass with the divergence intact. A table-driven test over the six is the shape that catches a seventh handler added later.

## Out of scope

`[path]` / `--cwd` resolution itself — that contract is settled and correct (both are resolved against the CLI's own cwd and must be existing directories). This task is only about `--config`'s base.

## Exit criteria

- [x] All six `--config` call sites agree on one resolution base, asserted by a test that covers all six — **or** the divergence has a row in [`accepted-behaviors.md`](../accepted-behaviors.md) and a statement at `docs/guide/cli.md:43`. — direction (A); the five CLI handlers by a table derived from `--help`, the MCP handler by its own package's tests plus a single-call-site source guard (see the note on why not one file).
- [x] The reproduced case (`lint proj --config cfg.json` from the parent directory) either finds the file or reports a path the user typed. — it finds the file, and the test asserts the config was _applied_ (its `REF-001` fires), not merely located.
- [x] The diagnostic renders the path against the same base it was resolved against. — `displayConfigPath` already anchored on `params.cwd`; moving resolution onto the same anchor is what collapses `../nope.json` to `nope.json`.
- [x] The deferral no longer lives only in `P11-remediation/10-cli-exit-contract.md`. — marked closed there; no register row, because nothing is accepted.
- [x] Gates green.

## Implementation notes

- **Direction (A), and no `accepted-behaviors.md` row.** The guide already implied the caller's `cwd` ("named relative to the directory the command works in"), the diagnostic anchor was already `params.cwd`, and (A) removes a divergence instead of documenting one. A register row records a behavior _accepted_ rather than fixed; this one is fixed, so a row would misrepresent the tree. The unifying rule now stated everywhere: **a relative config path resolves against the directory the command analyzes** — `[path]` for `lint`/`graph`, the CLI's own cwd for `slice`/`impact`, `--cwd` for `compile`, the tool `cwd` for the five file-based MCP tools.
- **The fix is one line; the ripple is not.** `path.resolve(params.explicitConfigPath)` → `path.resolve(params.cwd, …)` in `load-config.ts`, then both workarounds deleted (`handleCompile`'s pre-resolve, `tool-context.ts`'s `resolveConfigPath`). But `buildCiWorkflowYaml` emitted `lint '<configDir>' --config '<repo-root-relative path>'`, which under the new base resolves to `<dir>/<dir>/wastech-mdlint.config.json` — every generated workflow for a subdirectory config would have failed `CONFIG_NOT_FOUND` on its first run. It now emits the config's **basename**, since `configDir` is that path's own dirname by construction. `[path]` stays repo-root-relative because the workflow runs from the repo root; the two arguments are anchored differently on purpose, which is now the docblock's first point.
- **The workflow test now runs what was written.** `init.e2e.test.ts`'s "workflow lint command actually lints that subtree" case previously _mirrored_ the emitted command with hand-written absolute paths — which is exactly why the generator's relative form went unguarded. It now reads the emitted `run:` line, splits it with a small single-quote-aware tokenizer, and executes that argv verbatim from the repo root. Hand-mirroring a generated command tests the mirror.
- **The seventh-handler guard is runtime derivation, not a hand-kept list.** `packages/cli/test/config-resolution-base.test.ts` parses the command names out of `--help`, probes each one's own help for `--config <file>`, and asserts the derived set equals the parametrized table — so a sixth CLI command that grows the flag fails the equality check _and_ is covered by the table. The hidden `scan` alias is absent from root help by design; it is built by the same `addLintCommand` and dispatches to `handleLint`, so `lint`'s row covers it.
- **Why the six rows do not live in one file.** Neither host package declares `main`/`exports` (both `package.json`s carry only `bin`) and neither depends on the other, so a single file would need either a widened MCP public surface — which this task forbids — or a cross-package relative `src` import the repo has no precedent for (`boundary-guards.test.ts` _reads_ files across packages, it does not import them). Spawning both built binaries from one file would mean duplicating the JSON-RPC stdio harness for one row. The property the criterion protects is delivered on both sides instead: runtime derivation on the CLI, and on MCP a source-level guard asserting `loadConfiguration(` appears in exactly one file, so a seventh file-based tool cannot bypass the helper and reintroduce a second base.
- **The caller-visible change, stated plainly:** `lint <dir> --config <relative>` and `graph <dir> --config <relative>` change meaning. `lint --config x` with no `[path]` is unchanged (commander defaults `[path]` to the CLI cwd), and `slice`/`impact` are unchanged in production, since their analyzed directory _is_ the CLI cwd. The blast radius is exactly "a `[path]` plus a relative `--config`" — the reproduced case.
- **`resolveToolCwd` was not touched.** [P14.01](01-mcp-cwd-validation.md)'s contract — `cwd` validated before `loadConfiguration`, `INVALID_INPUT` pre-empting `CONFIG_NOT_FOUND` — survives byte-for-byte, and no input schema, tool registration, or tool was added: the MCP surface does not widen.
- **Docs.** `docs/guide/cli.md` (the rule under `lint`, the four `--config` rows, the `impact` bullet, and `compile` no longer being "unlike other commands" for this flag), `docs/guide/compile.md`, `docs/guide/configuration.md`, `docs/guide/mcp-server.md`, `README.md`, the glossary (`loadConfiguration`'s base, `compile`, the six tools, and `config-writer.ts`'s workflow template), plus the closing note on [P11.10](../P11-remediation/10-cli-exit-contract.md) and a superseded note on [P5.05](../P5-compile/05-compile-config-cli.md). No `npm run generate:docs`: no rule, option, or config key moved, so `packages/cli/schema.json` and README's rule table are unaffected.
