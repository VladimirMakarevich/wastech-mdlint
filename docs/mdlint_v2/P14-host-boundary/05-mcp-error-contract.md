# P14.05 · MCP error-contract parity and the operational code

> Phase: [P14 — Host boundary](index.md) · Roadmap: [v2 Index](../index.md) · Size **M** · Status **Done**. Backlog: [W-19](../remediation-backlog-2026-08-05.md) (Medium), [W-20](../remediation-backlog-2026-08-05.md) (Medium, **decision**), [W-21](../remediation-backlog-2026-08-05.md) (Medium, **decision**). Sources: field F-24, F-26; audit F19. Depends on [P14.01](01-mcp-cwd-validation.md).

## Goal

Make the MCP error surface carry, on every path, what the CLI already tells a user: the actionable sentence, a machine-readable code, and enough detail to act. Three defects, one contract — and two of them are decisions the taxonomy's own closed-set rule cannot resolve locally.

## Problem

**W-19 — the text block drops the `hint`.** On an unknown rule id, `structuredContent` carries the full contract (`code: "INVALID_INPUT"`, `message: 'Unknown rule "REF-01".'`, `hint: 'Did you mean "REF-001"?'`) but `content[].text` is only `Unknown rule "REF-01".` The CLI on the same typo prints `- rules[0]: Unknown rule "REF-01". Did you mean "REF-001"?` The text block is what a host renders and what a model reads, and the dropped sentence is the actionable half.

**It is an asymmetry, not a global rule** — verified by asserting `text.includes(structuredContent.hint)` across the error paths: `compile-context`/`COMPILE_CONFIG_MISSING` **yes**, `impact-analysis`/`TARGET_NOT_FOUND` **yes**, `lint`/`INVALID_INPUT` **no**. So the fix is local, in [`packages/mcp-server/src/tools/lint.ts`](../../../packages/mcp-server/src/tools/lint.ts) or the shared error wrapper. The `hint` is legitimately conditional: an unknown rule with no near-miss (`NOPE-999`) returns `{code, message}` only.

**W-20 — schema-level rejections bypass the contract entirely.** Any argument the tool's own `inputSchema` rejects returns `isError: true`, **no `structuredContent` at all**, and raw transport text: `MCP error -32602: Input validation error: Invalid arguments for tool context-slice: Too small: expected number to be >=0 at depth`. No `code`, no `hint`, and the `-32602` prefix leaks transport detail into user-facing text.

The field test's verdict: **acceptable to a human, useless to a program.** The message names the offending field (`at depth`, `at format`) and the constraint or valid set (`>=0`, `expected one of "json"|"summary"`), which is better than most validation errors — a human or a model reading the text can fix the call. But a host that branches on `code`, or surfaces `hint`, sees nothing.

**The mechanism is already written down in the tree**, at [`packages/core/src/config/config-schema.ts`](../../../packages/core/src/config/config-schema.ts) `:77-79`, three lines above the `ruleEntrySchema` declaration: the SDK validates tool input before the handler runs, so a rejected entry "would come back as raw InvalidParams text with no structuredContent instead of the M6 `{ code, message, hint }` payload". The [`glossary.md`](../glossary.md) **Error contract** entry states the same bound. So this is a known, recorded gap that has never been decided.

**W-21 — no operational error code.** Against one fixture (a directory `chmod`'d `000`): the CLI prints `Operational error: EACCES on docs/locked` and exits `2` — errno plus a normalized path. MCP `lint-files` returns `INTERNAL_ERROR` and "An unexpected internal error occurred." — no path, no errno, which is the whole actionable content.

**The conformant part:** `INTERNAL_ERROR` is what the taxonomy specifies for an unexpected throwable. What no document records is that the closed set has **no operational-error code at all**, so nothing will ever flag the asymmetry. `docs/guide/output.md:35` describes operational failures in CLI terms only. Widening `isStructuredError` to duck-type errno errors is explicitly the **wrong** fix and [`packages/core/src/errors.ts`](../../../packages/core/src/errors.ts) `:32` says why.

## Deliverables / steps

1. **W-19:** concatenate the `hint` into the text on the `lint`/`INVALID_INPUT` path, preferably in the shared error wrapper so a future path cannot regress. Assert `text.includes(hint)` for **every** error path that carries one — conditionally, since the `hint` is optional by design.
2. **W-19 — cover the rejections [P14.01](01-mcp-cwd-validation.md) adds.** Those are new `INVALID_INPUT` paths; they must satisfy this assertion from the day they land, which is why P14.01 comes first.
3. **W-20 — decide:** pre-validate inside the handler so the contract owns every path (the tool's wire schema then has to accept every shape it wants to reject with a proper payload — the glossary already states this consequence), **or** document that schema rejections are contract-exempt, with a register row plus a line in the guide where the contract is documented. Note that direction one is a real design change: loosening `inputSchema` to permit a shape only so the handler can reject it better is a trade, not a free win.
4. **W-21 — decide, and it cannot be closed locally:** add an operational code to `TOOL_ERROR_CODES` **and amend the decision entry** at `docs/mdlint_v2/decisions/pre-implementation-decisions.md:57` in the same change, as that log's own honesty rule requires; **or** keep the closed set and register the asymmetry. Either way `docs/guide/output.md:35` stops describing operational failures in CLI terms only.
5. **State the caller-visible consequence.** A host matching on `INTERNAL_ERROR` breaks if a new code is introduced. Say so in the change, as [P14.01](01-mcp-cwd-validation.md) does for its own.
6. **Glossary.** The **Error contract** entry lists the closed code set and states the pre-handler-validation bound. Whatever these three decisions produce, that entry is where it lands.

## Out of scope

Duck-typing errno errors into `isStructuredError` — ruled out with the reason in code. Adding mutating MCP tools or a non-stdio transport: outside the v2 security boundary.

## Implementation notes

- **Caller-visible consequence, stated plainly: a host matching on `INTERNAL_ERROR` breaks, and so does one string-matching an exact error message.** A failure carrying an errno and a path inside the tool's `cwd` — an unreadable directory, an unreadable config — used to return `INTERNAL_ERROR` with "An unexpected internal error occurred."; it now returns `OPERATIONAL_ERROR` with `Operational error: EACCES on docs/locked`. `INTERNAL_ERROR` remains for everything else, so the break is narrow, and all three packages are `0.0.0` with nothing published. Separately, every error text block that carries a `hint` is now longer — that is W-19's whole point, but an exact-match assertion on the old text fails.
- **W-20 decided: schema rejections stay contract-exempt.** Pre-validating inside the handler means loosening every tool's advertised `inputSchema` to a shape it intends to reject, which destroys the discoverability contract a host or model uses to _construct_ a valid call; the tree already prices that trade at [`config-schema.ts`](../../../packages/core/src/config/config-schema.ts) `:74-81`. The shipped policy is already _selective_ loosening exactly where guidance pays (P12.04's `z.union([customRuleEntrySchema, ruleEntrySchema])`), and writing that down is the honest form.
- **The task file's quoted `-32602` text does not match the tree** and the guide quotes the tree instead. The pinned SDK (1.29) renders the Zod issues as a JSON array — `Invalid arguments for tool context-slice: [ { "code": "too_small", …, "path": ["depth"] } ]` — not the flattened `Too small: expected number to be >=0 at depth` the problem statement shows. Every substantive claim holds (no `structuredContent`, the transport number leaks, the field and constraint are named); only the rendering differs, and `stdio-integration.test.ts` now pins the real one so a future SDK change fails the suite that the guide's prose depends on.
- **W-21 decided: the code was added, not registered.** The phase goal is to carry "what the CLI already tells a user … enough detail to act", and errno-plus-path _is_ that content. Core owns the code; the classifier is host work (`shared/operational-error.ts`), the same split `INVALID_INPUT`/`ToolInputError` already uses, so `isStructuredError` is untouched and a raw errno still cannot duck-type through — `errors.test.ts`'s raw-`ENOENT` case is the paired guard.
- **`errorResult` owns both fixes**, so a newly added error path inherits them. The hint concatenation skips a message that already contains its hint: `CompileConfigMissingError`, `ImpactAnalysisError` and a `CONFIG_INVALID` `ConfigError` interpolate their own hint _into_ the message, so a blind concatenation would have printed those sentences twice — which is also why the two paths the audit found already passing passed by accident rather than by rule.
- **The signature became an options object** (`{ successFields?, cwd? }`). All six call sites changed anyway, and `compile-context` supplies a `cwd` with no placeholders, which positionally would have meant a mid-list `undefined`.
- **`toolCwdBase` was split out of `resolveToolCwd`.** Each tool computes it _above_ its `try`, because `resolveToolConfiguration`/`resolveToolContext` are themselves throw sites — an errno raised while resolving has no `loaded.cwd` to render against. P14.01's exit criterion (`cwd ?? process.cwd()` in one place) still holds: `resolveToolCwd` calls the same helper. `lint` has no `cwd` input and passes `process.cwd()`, the same base as its `rootDir`.
- **Two deliberate bounds on what `OPERATIONAL_ERROR` will name**, both in the [register](../accepted-behaviors.md): a path outside the `cwd`, and an errno with no `path` at all (POSIX raises `EISDIR` from the `read` syscall, which carries none). Both stay a sanitized `INTERNAL_ERROR`. This is stricter than the CLI's renderer on purpose — the property being protected is "no payload names a host path the caller did not itself _supply_", not the stronger "no absolute path at all": the `cwd` is itself echoed back absolutely by [P14.01](01-mcp-cwd-validation.md)'s `INVALID_INPUT` rejection, where the value is the caller's own and is the thing being reported. Across Windows drives `path.relative` returns an absolute path outright, which is why the bound is checked rather than assumed. (This bullet said "outside the analyzed directory" until [P18.05](../P18-followup-burndown/05-doc-claims.md) — a phrasing `displayConfigPath` already contradicted, since a caller's own `configPath` is rendered relative to `cwd` with no containment check.)
- **A `cwd` that fails to stat for a non-`ENOENT`/`ENOTDIR` reason is now actionable**, which is the follow-through P14.01's last implementation note deferred here. `stat` on a `0o000` directory succeeds (the permission bit lives on the parent), so the failure actually surfaces from the corpus walk's `readdir`, naming the analyzed directory as `.` — pinned by its own unit case.
- **The end-to-end evidence needs `chmod`, so it is `skipIf`-guarded.** The plan's proposed portable trigger — a `configPath` naming a directory — does not work: on macOS and Linux `readFile` on a directory fails at the `read` syscall, and that error carries no `path` (verified). Root ignores directory permissions and Windows does not model them, so the real-filesystem cases in `lint-files.test.ts` and `stdio-integration.test.ts` use the repo's existing `it.skipIf(win32 || getuid() === 0)` pattern, and the portable half is five synthetic-errno cases in `tool-response.test.ts` that run everywhere.
- **Honest reading of one exit criterion.** "A test that fails before its fix" holds for W-19 (two red assertions) and W-21 (`expected 'INTERNAL_ERROR' to be 'OPERATIONAL_ERROR'`). W-20's outcome is a documented exemption, so its test is a **characterization pin** that passed before and passes after; its value is failing if an SDK upgrade or a later decision changes the shape the guide describes to users.
- **No new `@boundary-guard` category.** `stdio-integration.test.ts` is already tagged `installed-bin-spawn`, and the new wire cases sit inside it; [`boundary-guards.test.ts`](../../../packages/core/test/boundary-guards.test.ts) needed no edit.
