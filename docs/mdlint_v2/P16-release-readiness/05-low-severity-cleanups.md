# P16.05 · Low-severity code and decision cleanups

> Phase: [P16 — Release readiness](index.md) · Roadmap: [v2 Index](../index.md) · Size **S–M** · Status **Done**. Backlog: [W-37](../remediation-backlog-2026-08-05.md) (Low), [W-38](../remediation-backlog-2026-08-05.md) (Low), [W-39](../remediation-backlog-2026-08-05.md) (Low, **decision**), [W-40](../remediation-backlog-2026-08-05.md) (Low, **decision**). ## Goal

Clear the four smallest code and scope items, two of which are one-line fixes and two of which are decisions that only need to be **made** — a scope choice left unstated is what turns into a finding a second time.

## Problem

**W-37 — the generated schema hardcodes the custom `target` vocabulary twice.** [`packages/core/src/engine/schema.ts`](../../../packages/core/src/engine/schema.ts) `:88` and `:104` each spell the enum as a literal (`["checklist", "content", "link", "section", "table"]`) while the typed authority is `ASSERTION_TARGETS`. **Correct today** — the values were compared and match. The finding is that a new assert kind with a new target needs two hand edits in a function whose own framing is metadata-driven, and that the config loader is **looser** than the schema (`config-schema.ts:98` accepts any string), so drift would present as "the editor rejects a config the linter accepts" — a confusing shape to debug.

**W-38 — a stale rationale comment.** [`packages/core/src/graph/coverage.ts`](../../../packages/core/src/graph/coverage.ts) `:73-74` still says the coverage signal is "Core-only for P4.06 — there is no CLI/lint-output consumer yet". There is: [`packages/cli/src/commands.ts`](../../../packages/cli/src/commands.ts) `:232` calls it. The QA pass added a detail the audit omitted: the comment **continues** "(P4.07 surfaces this in the `graph` command)", so it points at the consumer that arrived. The fix is to delete the stale half, not the whole comment.

**W-39 — `init` can only ever infer 8 of the 24 built-in rules.** The inference vocabulary is `CTX-001 CTX-002 GRP-001 REF-001 REF-002 REF-003 SEC-001 TBL-002`. The other 16 — including `SIZE-001` and `LLM-001`, the two LLM-context rules the README **leads with** — are never proposed, so a user reaches them only by reading the rule table and hand-writing config. Concretely reachable for a real target: the scan already samples file sizes, so a derived `SIZE-001` budget is inferrable; `CLAUDE.md`/`AGENTS.md` with `@` imports are detectable, so `LLM-001` is too. Recorded as a scope choice rather than a defect — but combined with [P13.04](../P13-correctness/04-rule-option-defaults.md) it means **nothing guides a user to a working size budget from either direction**, and P13.04 fixes only the config-authoring half.

**W-40 — four uncalled barrel exports.** `slice`, the single-document `extractDocProfile`, the `fileMatches` hook on assertion options, and the retained `files` option on the column-unique primitive have no host caller, against a barrel whose own comment frames hosts as the audience and a coding rule against extension points built ahead of need.

**Genuinely a judgment call:** `core` is a published package, so "no internal caller" is not automatically a defect, and no document names an expected consumer for these four. `getImpactSet` and `query` are **not** in this item — a tier-3 decision names both as consumed, which makes them a documented expectation the code does not meet rather than an open call, and they live in [P17.03](../P17-plan-of-record/03-adr-and-dependency-register.md).

## Implementation notes

**Two premises in this task file were stale, and are corrected here rather than silently worked around.** The cited line numbers had drifted: the `target` literals are `schema.ts:101` and `:117`, not `:88`/`:104`, and the `coverage.ts` clause is at `:75-76`, not `:73-74`. More load-bearing, W-39's "the scan already samples file sizes" is **not true** — `collectMarkdownFiles` (`discovery/repo-scan.ts`) walks with `readdir` and never `stat`s, and `DocCluster` carries `subtreeCount`, a Markdown file **count**. Nothing in `RepoScanResult` measures bytes, lines, or tokens. The premise is salvageable one layer up — `inferRuleSet` re-parses each sample and holds `ParsedDocument.content` — but only for the 3–5 sampled files per cluster, which is the distinction the decision below turns on.

**W-37 — derived, with the loader left loose on purpose.** `schema.ts` now imports `ASSERTION_TARGETS` on the same line it already imported `assertionSchema` from (no new module edge) and derives `ASSERTION_TARGET_ENUM = [...new Set(Object.values(ASSERTION_TARGETS))].sort()`, wrapped in a `targetProperty()` helper mirroring the existing `severityProperty()` — the spread is what stops the generated JSON aliasing the shared array. Both branches call it. The output is byte-identical, so `packages/cli/schema.json` needed no regeneration and the R6 byte-sync test proves it. Nothing asserted the generated enum before — the byte-sync test only proves the file matches whatever the generator produces — so a guard was added pinning **both** custom branches (generic and known-custom-id) to the sorted distinct values, since either could have drifted alone.

The loader's `target: z.string().optional()` stays, with the reason in a comment beside it. The asymmetry does not point the direction the finding assumed: `resolveCustomRule` is **stricter** than any enum, because it validates the target against the _specific_ assert kind (`target "heading" does not match assert kind "sectionPresent" (expected "section")`), and a `z.enum` would preempt that with a generic Zod message. `customRuleEntrySchema` is also the MCP `lint` tool's wire schema (`mcp-server/src/tools/lint.ts`), where a pre-handler rejection escapes the M6 `{ code, message, hint }` contract entirely — the exemption already recorded in the register. And the confusing shape the finding describes, "the editor rejects a config the linter accepts", cannot arise now that both enums read `ASSERTION_TARGETS`: the schema is a coarse pre-filter over the same authority, and the loader defers the verdict to the one place that can give a useful one.

**W-38 — the seam was doubly closed.** Beyond the CLI `graph` command the comment itself anticipated (`cli/src/commands.ts`, both formats), the MCP `context-graph` tool's `summary` branch calls `computeGraphCoverage` directly since P15.02/W-22. The replacement names both consumers rather than only deleting the stale half.

**W-39 — not widened; the choice is recorded and, more to the point, disclosed.** Both candidates are budgets with **required** options. `SIZE-001` needs at least one of `bytes`/`lines`/`tokens` — a bare `{"rule":"SIZE-001"}` fails config load — and `LLM-001` needs `entrypoints` **and** `maxTokensPerEntrypoint`. `entrypoints` is derivable; the budget is not. Inference sees 3–5 files per cluster, and `LLM-001` measures the full transitive `@`-import closure, which inference never builds — so a threshold derived there would be invented, and would reach the user looking measured. That is the same objection [P13.04](../P13-correctness/04-rule-option-defaults.md) raised when it declined to ship `SIZE-001` defaults ("any byte or line count picked here would be arbitrary"), now answered from the inference side too, so neither direction fabricates a number.

What changed instead is that the absence stopped being silent. The `init` draft now closes with a `Not proposed by init:` block naming both rules, why neither can be inferred, and their guide pages — the same disclosure discipline as the `Excluded from the scan:` block above it (P14.03's "what makes it survivable is disclosure, not omission"). It is unconditional, `merge` included, because it states what `init` proposes rather than what the resulting config contains. `docs/guide/cli.md`'s `init` section carries the prose home the register requires for a user-facing row, and `rule-inference.ts`'s "why these 7" comment now points here as well as at P6.02, so the next reader meets the re-affirmation rather than only the original.

Two register rows were re-pointed rather than left aimed at an open item: the dot-directory prune row, whose "widening what `init` infers is W-39" now reads as the settled answer, and the `GRP-001`-rationale residual, which expected to travel with the widening — it now has no owner and falls to whoever next touches `rule-inference.ts`. The glossary is unchanged, as deliverable 6 makes its `init`/`scanRepository` entries conditional on widening.

**W-40 — all four removed.** No document names a consumer for any of them (which is exactly what separates them from `query`/`getImpactSet`), and [coding-style.md](../../../.agents/rules/coding-style.md) bars extension points ahead of need. `slice` was a six-line wrapper over `query` with one test caller; the CLI `slice` command and the MCP `context-slice` tool never touched it, both going through `getContextSlice`. The singular `extractDocProfile` was deleted outright, not just unexported: with the barrel line gone its only callers were the tests written for it, so those moved to `extractDocProfiles([doc], graph, opts)` behind a local `profileOne` helper — and the corpus-vs-one-at-a-time comparison that used to prove the two entry points agree now proves the shared edge index does not alias between profiles, which is the failure that entry point can actually have. `RunAssertionOptions.fileMatches` was never passed by anything: `custom.ts` omits the argument, and the one project-scoped kind is dispatched to `columnUnique` directly with the rule's own scope matcher, so `runAssertion`'s `columnUnique` branch is unreachable in production and `?? (() => true)` always won — removing the option is behavior-preserving, and the branch now says so. `ColumnUniqueOptions.files` was passed by two call sites and read by none; P11.05 kept it as "a documented, deliberate wart" under a no-restructuring constraint that does not apply here.

**`query` and `getImpactSet` are deliberately untouched.** Both are named by decision entry 4.3 as reused by P7.03, which makes them a documented expectation the code does not meet rather than an open judgment call, and [P17.03](../P17-plan-of-record/03-adr-and-dependency-register.md) (W-47) owns settling them — including the option of recording them as intended library surface. Since P16 runs first, this task could neither wait on that outcome nor pre-empt it: the barrel now carries one line beside those two exports stating why they stayed while their four neighbours went, which P17.03 extends or replaces rather than reopening.

**Left for the P17 plan-of-record sweep.** Completed phase task files (P5.02, P12.03, P11.05, P4.08, the P1 index) and the audit reports still name `extractDocProfile`, `slice`, and the `files` option — they record what was true when written, and rewriting them would be rewriting history. `docs/mdlint_v2/index.md`'s Phase 5 bullet names `extractDocProfile` too, but that block is the forward-looking plan of record, which [W-42/W-43](../remediation-backlog-2026-08-05.md) own. The glossary — the live vocabulary register AGENTS.md requires kept current — was updated for all three symbols.
