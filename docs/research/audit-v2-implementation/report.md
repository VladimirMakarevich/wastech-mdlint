# Deep audit of the v2 implementation against the plan of record

## The question, and the answer

The question was not "what does this code do" but "where does the shipped v2 implementation of `wastech-mdlint` fail to do what the plan of record, the locked requirements, and the repository's own rules say it does". Three classes of finding carried equal weight: **inaccuracies** (code contradicting a documented invariant, requirement, decision, or exit criterion), **gaps** (a phase marked complete whose criteria are thin or unimplemented; a load-bearing behavior with no test; a cross-phase seam left as a placeholder and never revisited), and **problem areas** (fragile logic, validation that does not validate, duplicated implementations of one rule, abstractions built ahead of need).

**Headline conclusion: the pipeline is in materially better shape than the paperwork around it, with one exception that is a genuine correctness defect.** All eight architecture invariants in `AGENTS.md` hold in product code. The full suite passes — 67 test files, 850 tests, 6 skipped, all six Windows-gated. Every deferred requirement is genuinely absent from the code. Compile output is byte-deterministic across runs. The installed-bin spawn path, the exit-code taxonomy, path containment for the rules that reach the filesystem, and inline-disable suppression were each followed from a boundary to the code that satisfies them and then reproduced by running the product.

Against that, two findings are graded HIGH, and they are severe in two different ways — a distinction worth keeping, because they are not interchangeable. **F1 is a wrong answer to a user.** It is a correctness defect in the single glob matcher every configuration surface funnels through: a `!`-prefixed pattern in `include`, `exclude`, or any rule's `files`/`exclude` is evaluated as an independent OR term rather than as a subtraction, so it silently widens or empties the scope it was written to narrow. One reproduced shape prints `No problems found.` and exits `0` on a repository with real findings; another pulls a non-Markdown file into the corpus. The repository already diagnosed this exact hazard, wrote the reason down, fixed it, and pinned it with two passing tests — roughly 200 lines away, applied to workspace globs only. **F2 is a wrong answer to a maintainer**, with no user-visible symptom at all: the plan has no reliable completion surface in either direction — 91 exit criteria across 29 `Status **Done**` task files are unchecked while their phase indexes are fully ticked, and 33 phase-index criteria are unchecked across five phases whose task files all read `Done`, including four indexes that the very commit landing P11 and P12 rewrote line by line and left saying `Not started`. Of the 78 index criteria, only two are not met in code, so F2's demonstrated harm is that nobody can tell that from the plan. That harm is graded alongside F1 rather than with the documentation tranche below it for one concrete reason, not for emphasis: F5, F6, F7, F16, and F20 mislead a reader about where a document is or what a phase is called, while F2 misleads about whether work exists — in both directions, over 124 criteria — and it has already produced a wrong belief about a release gate. "`npm pack --dry-run` is clean per package" is ticked at `docs/mdlint_v2/P0-foundations/index.md:43` and open at `docs/mdlint_v2/P-release/index.md:39`, and `release:check`, the only local command documented to check it, validates none of it (F21, F23). It is still not the same kind of failure as F1.

The rest divides into a large, low-risk documentation-drift class (a phase rename that never reached shipped artifacts, a deleted report still linked 11 times, a config reference that inverts a default) and a smaller class of real behavioral divergences at the host boundary (a nonexistent MCP `cwd` returning success, `--config` resolving against two different bases across six handlers, one lint capability with two JSON shapes).

## Method: what was reproduced, and what rests on reading

Evidence comes from three upstream analysis passes — core (`packages/core/src`), surfaces (entry points, adapters, packaging, generated schema), and plan-of-record plus tests — and from this pass's own execution against the working tree at `d96b64c`. Where a claim could be settled by running something, it was: the built CLI over purpose-made fixtures in a scratch directory outside the repository, the MCP server over real stdio through the SDK client, real `git` for delivery history and for `.gitignore` semantics, `micromatch` directly for library semantics, `npm pack --dry-run` at the root and per workspace (including with `--foreground-scripts`, to see which lifecycle hooks actually fire), the project's own test suite after a build, and `tsc -b` in an isolated probe project. Nothing in the repository was weakened, stubbed, or modified to make a reproduction work; `tsc -b` was run first so the spawn-based checks would exercise current output.

Each finding carries a **Verification** line that says either _reproduced_ (naming what was run) or _by reading_ (citation only). The severity index repeats that marker so it survives skimming.

Four upstream claims did not survive re-checking and are recorded as withdrawn rather than quietly dropped: that the REF-004 rationale comment describes changed code (it does not — F26), that the roadmap's rule-count sentence is arithmetically wrong (it is ambiguous, not wrong — Open questions), that unhandled filesystem errors surface as a raw Node error at the user-visible boundary (the CLI handles them correctly; the real finding is the CLI/MCP asymmetry — F19), and that a rationale comment in the MCP server misattributes an SDK validation (the comment says "the SDK", which is accurate of the SDK's client — F29, withdrawn in full and kept as a numbered entry so the withdrawal is visible).

The findings are numbered **F1–F41**, of which F29 is withdrawn, leaving 40 live findings. Each withdrawal is stated at the number it belongs to rather than deleted.

### P2 — Rule engine, configuration, and discovery

#### F1 · HIGH · A `!` negation in any glob list widens or empties scope instead of subtracting from it

**What is wrong.** `matchesConfigGlob` is the single matcher behind every glob surface in the product, and it calls `micromatch.isMatch` with the whole pattern array (`packages/core/src/discovery/globs.ts:37`). That call is a first-truthy OR across the list, and a `!`-prefixed entry compiles to an _inverting_ matcher — so `["docs/public/**", "!docs/private/**"]` means "under `docs/public` **or** not under `docs/private`", which is true for almost every path in a repository. A second failure mode lives in the same helper: `normalizeConfigGlob` rewrites any slash-free pattern to a depth-agnostic form (`packages/core/src/discovery/globs.ts:14`), so a bare `!keep.md` becomes a literal filename pattern and is a silent no-op. Nothing validates or rejects a leading `!`.

**Evidence, and the class.** The repository already knows this distinction and applied the fix in exactly one place: `packages/core/src/discovery/workspace-packages.ts:249` states in prose that an ordered negation "never actually excludes anything" with `isMatch`, `:254` uses the list form that behaves correctly, `packages/core/src/types/micromatch.d.ts:8` records the semantics in an ambient declaration, and two tests pin it (`packages/core/test/workspace-packages.test.ts:195`). The load-bearing matcher was never converted. Grepping `matchesConfigGlob|matchesFileScope` across `packages/core/src` gives the blast radius: top-level `include` (`packages/core/src/markdown/load-documents.ts:109`) and `exclude`, directory pruning, every rule's `files`/`exclude` through the shared scope helper, `LLM-001.entrypoints`, `SIZE-001.overrides.pattern`, `CTX-003.glossary`, `REF-006` definitions and references, `GRP-002.entryPoints`, `GRP-003.chain[].files`, `STR-001` glob entries, REF-001/REF-003 target `exclude`, and `SEC-001`'s inferred scope. The dedicated test file for the shared matcher contains no ordered-negation case at all — its one `!` is an extglob syntax check (`packages/core/test/rule-utils.test.ts:14` is its `describe`).

**Plan clause violated.** This is the "validation that does not validate" class named in the audit brief, and it defeats `docs/guide/configuration.md:47`'s promise that `exclude` wins over `include`. Negation is not an advertised feature in `docs/guide/configuration.md` or `docs/guide/config-reference.md`, so this is a latent trap rather than a broken documented feature — which is why it is graded on impact rather than on contract.

**Why it matters.** Two of the four reproduced shapes are silent: one reports a clean repository that is not clean, and one lints files the author believed were out of scope. A linter that under-reports on a scoping typo is worse than one that errors.

**Remediation.** Route `matchesConfigGlob` through the list form already used at `packages/core/src/discovery/workspace-packages.ts:254`, and normalize a leading `!` before the depth-agnostic prefix is applied — or reject a leading `!` during config validation. Close it in `packages/core/src/discovery/globs.ts`, and add the ordered-negation case to `packages/core/test/rule-utils.test.ts`, which is where its absence let this ship.

**Verification — reproduced, eight ways, through the built CLI, and re-confirmed independently.** With `include: ["docs/**", "!docs/private/**"]` the corpus became `README.md`, `docs/private/secret.md`, `docs/public/a.md`, `notes.txt`, and `wastech-mdlint.config.json` — the whole tree, including a non-Markdown file, and _including_ the directory the negation named. With `exclude: ["docs/private/**", "!docs/private/keepme.md"]` the corpus emptied and the run printed `No problems found.` with exit `0` where the same corpus without that one entry reported an error and exited `1`. Adding `"!docs/private/**"` to a rule's `files: ["docs/public/**"]` pulled a third file, `docs/other/c.md`, into that rule's scope. A slash-free `exclude: ["!a.md"]` changed nothing. Directly against the library: `micromatch.isMatch("README.md", ["docs/**", "!docs/private/**"], {dot:true})` is `true`, while the list form `micromatch(paths, patterns)` returns exactly the intended single path.

The first two shapes were then re-run from scratch on a second fixture built independently of the first, and behaved identically: the negated `include` produced a six-file corpus — `README.md`, `docs/other/c.md`, `docs/private/secret.md`, `docs/public/a.md`, `notes.txt`, `wastech-mdlint.config.json` — while the negated `exclude` printed `No problems found.` and exited `0` against a control run of the same config, minus the negation, that exited `1`. This is the finding to trust least on citation alone and most on execution, and it survived both.

## Recommended approach, and its trade-offs

The findings split cleanly into three tranches, and the ordering below is a triage judgment, not a severity assignment — the severity of each finding is the one in its own heading.

**First: F1 alone.** It is the only finding where the product silently reports the wrong answer, and it is unusually cheap to close because the fix, the rationale, and the tests already exist in the tree for the workspace variant. The trade-off is real and should be decided deliberately: switching `matchesConfigGlob` to the list form changes the meaning of any configuration that currently contains a `!` entry. Anyone relying on today's accidental widening would see their corpus shrink. The alternative — rejecting a leading `!` at config validation — is a smaller behavioral change and turns a silent wrong answer into a loud one, at the cost of not delivering negation as a feature. Either way the regression test belongs in `packages/core/test/rule-utils.test.ts`, whose silence on this case is what let it ship.

**Second: the boundary findings — F3, F4, F10, F19.** Each converts a silent or misattributed result into an accurate one, and each is a small change at named call sites — F3 is one stat-and-reject, though it has to land at all four places the MCP root is defaulted rather than only in the shared resolver. The trade-off is that both MCP findings change responses an agent may already be handling: F3 makes previously-successful calls fail, and F19 changes the code and message on a call that already fails, which breaks a caller matching on `INTERNAL_ERROR`. Both are the correct direction and both are caller-visible. F19 additionally cannot be closed locally: adding an operational code means amending a decision record that defines the set as closed.

**Third: the documentation-drift tranche — F2, F5, F6, F7, F12, F16, F18, F20, F32, F35, F39, F41.** These are individually trivial and collectively the largest class in the report, and they share one cause: a rename, deletion, or scope change that was applied in one place and never swept. Two of them sit in the precedence tiers a contributor is told to obey rather than in user-facing pages — the enforced architecture decision (F32) and the cross-phase dependency register (F39) — so they are the ones most likely to make a future change wrong rather than merely to confuse a reader; both are cheap and should go first inside this tranche. The highest-leverage action is not the individual edits but making the class visible — this repository ships the rule that catches F6 and has no configuration to run it on itself (**F35**). No document records a decision against a repository configuration; two — requirement I8 at `docs/mdlint_v2/requirements/06-installation.md:38` and `docs/mdlint_v2/glossary.md:305` — presume one already exists in the v2 shape. So adding a narrow docs-only configuration and a CI step that runs it closes a plan expectation rather than reversing a decision, and it is the one change that would turn this tranche from an audit finding into a build failure. The alternative is to accept that link rot in the plan is found by audit rather than by CI, and to record that choice in the register instead of leaving it unstated. F2 should be resolved by decision, not by ticking boxes: 91 checkboxes that no process maintains are worse than none.

Explicitly **not** recommended: any redesign. Every finding here names a specific line and a specific fix direction, and the architecture they sit inside was checked invariant by invariant and holds.
